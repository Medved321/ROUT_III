## Context

Сейчас весь обмен идёт одним UDP-сокетом: кадр `[1B type][2B seq][payload]` (`shared/protocol.py`), сервер и клиент на `asyncio` DatagramProtocol, `SelectorEventLoop` на Windows (`shared/asyncio_util.py`). Уже есть PING/PONG с измерением RTT (`network_client.py:74`, `server/server.py:187`). Мотивация — see `proposal.md`.

Ограничения, которые формируют подход:

- Конвенция проекта: протокол без согласования не меняем (`openspec/specs/001-doom-shooter.md:51`) — здесь согласование как раз оформлено этим change.
- Модель игры завязана на `TICK_RATE = 20` (`server/game_data.py:9`); игровой обмен должен остаться максимально дешёвым.
- Запуск клиента — исходники из корня (`run_client.py`), ассеты грузятся относительными путями (`client/assets.py:8`), поэтому обновляем код, а не контент.

## Goals / Non-Goals

**Goals:**

- Надёжная доставка управляющих команд и файла клиента поверх одного UDP-сокета.
- Явное согласование версий протокола и клиента при подключении.
- Рабочая процедура доставки и применения новой версии клиента.
- Минимальные вторжения в игровой путь: ввод/снапшоты не ретранслируются.

**Non-Goals:**

- Клиентское предсказание движения/камеры и интерполяция удалённых сущностей — отдельный change #2.
- Изменение игровой симуляции, баланса, карт.
- Сжатие/дельта-кодирование снапшотов (см. change #2).
- Подпись пакетов (HMAC) — см. Open Questions.

## Decisions

### 1. Надёжный слой поверх текущего UDP-сокета

Музыка: один `DatagramTransport`, два логических канала — ненадёжный (игра) и надёжный (управление + файл). Отдельный `shared/reliability.py` с endpoint'ом, который владеет окном, таймерами и сборкой.

Альтернативы: TCP control-plane или HTTP для файла — отклонены: второй сокет, другая модель, разрозненный хендшейк (выбор зафиксирован в обсуждении).

### 2. Формат кадра и мультиплексирование

```
[1B type][2B seq]                         существующий заголовок (seq = reliable seq)
RELIABLE_DATA payload:
  [2B ack]                                старший полученный seq
  [4B ack_bits]                           селективная маска (32 назад)
  [1B inner_type]                         JOIN / LOBBY / PARTY / FILE_*
  [1B frag_index][1B frag_count]          0/1 для неразделённых сообщений
  [payload <= budget]                     бюджет ~1000B (MTU-safe)
```

ACK вкладывается в ненадёжные/надёжные исходящие кадры; при простое отправляется отдельный `ACK`-кадр. Тип `RELIABLE_DATA` не ретранслируется вслепую: решение о повторе принимает endpoint по окну.

### 3. Управляющие команды: порядок + идемпотентность

Команды (`HELLO`, лобби, создание/вход/выход из партии) идут надёжно и по порядку. Каждая несёт `request_id`; сервер помнит последний обработанный `request_id` на сессию и игнорирует повтор. Это делает ретрансмит безопасным.

### 4. Передача файла: фрагменты + битмап + sha256

Файл бьётся на фрагменты фиксированного размера. Получатель ведёт битмап и селективно подтверждает; отправитель досылает только дыры. По завершении — sha256. Файловый канал не требует упорядочивания (важен индекс/смещение), поэтому head-of-line блокировки нет.

### 5. RTO и окно

Базовый RTO — от текущего PING RTT (минимум ~100 мс), с экспоненциальным backoff; размер окна небольшой (порядка 8–32 фрагментов) до появления данных о пропускной способности. Исчерпание попыток -> сессия помечается недоступной, клиент показывает разрыв.

### 6. Хендшейк версий и bootstrap

Вводим `HELLO{protocol_version, client_version}` первым обменом; ответ `HELLO_ACK{server_protocol, client_version, update?}`. При несовместимом протоколе — отказ с причиной. Формат `HELLO`/`HELLO_ACK` фиксируем как стабильный. Первую версию с хендшейком ставим вручную (текущие клиенты её не знают).

### 7. Упаковка клиента и применение

Клиент собирается в версионный артефакт (`releases/rout-client-<ver>.<ext>`), внутри — `client/` и `shared/`; `assets/` остаётся рядом и не пересылается. Применение: скачать во временный файл -> проверить sha256 -> сохранить отдельным версионным файлом -> обновить указатель актуальной версии -> перезапуститься на новом файле. Работающий файл не перезаписывается (Windows блокирует/держит zipimport).

Альтернатива — zip с деревом исходников: отклонена из-за частичных обновлений и проблем перезаписи на Windows.

### 8. Режим применения: подтверждение по умолчанию

Сервер шлёт исполняемый код — это RCE на всех клиентах. Поэтому по умолчанию клиент спрашивает подтверждение; авто-режим — только через явную настройку. sha256 ловит порчу, но не подмену (MITM).

### 9. Поток управления внутри существующего loop

Endpoint проверяет таймеры (RTO, сбор файла) по расписанию в том же asyncio-loop, без новых потоков. Это сохраняет простую однопоточную модель; тяжёлая запись файла на диск делается после полного приёма в памяти/во временном файле.

## Risks / Trade-offs

- [Свой транспорт — ошибки в RTO/окне/краевых случаях] -> маленькое фиксированное окно, backoff, тест с эмуляцией потерь/дублей/перестановок.
- [Windows блокирует работающий файл] -> версионные файлы + переключение указателя, без перезаписи запущенного.
- [RCE при раздаче кода] -> подтверждение по умолчанию, sha256, доверенный сервер; HMAC отложен.
- [Bootstrap: текущие клиенты не понимают апдейт] -> первая версия ставится вручную, дальше автоматом.
- [Фрагментация UDP при превышении MTU] -> бюджет датаграммы, фрагментация на уровне протокола.
- [Старый/несовместимый клиент продолжает слать] -> сервер отклоняет по версии протокола.

## Migration Plan

1. Протокольная версия поднимается; сервер начинает отвечать `HELLO_ACK`.
2. Первый клиент с хендшейком и апдейтером устанавливается вручную на машины.
3. На сервере появляется `releases/` с актуальным артефактом; дальнейшие обновления — по сети.
4. Откат: указатель версии возвращается на предыдущий артефакт (старые версии хранятся).
