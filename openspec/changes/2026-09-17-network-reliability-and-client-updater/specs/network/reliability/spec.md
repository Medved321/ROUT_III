## Purpose

Обеспечивает надёжную доставку управляющих сообщений и файлов поверх одного UDP-сокета, оставляя игровой обмен ненадёжным и быстрым.

## ADDED Requirements

### Requirement: Reliable delivery

Сообщения, отправленные по надёжному каналу, MUST доставляться получателю ровно один раз и в порядке отправки, несмотря на потери, дублирование и переупорядочивание датаграмм.

#### Scenario: Потеря датаграммы

- **WHEN** датаграмма с надёжным сообщением потеряна
- **THEN** отправитель повторяет её до получения подтверждения
- **AND** получатель доставляет сообщение приложение ровно один раз

#### Scenario: Дубликат

- **WHEN** одна и та же надёжная датаграмма приходит дважды
- **THEN** получатель игнорирует повтор и не доставляет сообщение повторно

### Requirement: Selective acknowledgment

Получатель MUST подтверждать приём надёжных датаграмм, а отправитель MUST повторять только неподтверждённые, не превышая размер окна.

#### Scenario: Потеря середины окна

- **WHEN** из окна доставлены все датаграммы, кроме одной
- **THEN** отправитель по подтверждениям определяет отсутствующую и повторяет только её

### Requirement: Adaptive retransmission timeout

Таймаут повторной передачи SHALL оцениваться по измеренной задержке (RTT), а исчерпание попыток MUST помечать сессию как недоступную.

#### Scenario: Нет подтверждения

- **WHEN** подтверждение не приходит в течение таймаута
- **THEN** датаграмма отправляется повторно с увеличенным интервалом
- **AND** после исчерпания попыток сессия считается разорванной

### Requirement: File transfer with integrity

Передача файла MUST выполняться фрагментами, размер фрагмента MUST укладываться в бюджет одной датаграммы; сборка MUST проверяться по контрольной сумме.

#### Scenario: Потерянные фрагменты

- **WHEN** часть фрагментов файла потеряна
- **THEN** отправитель досылает только отсутствующие
- **AND** получатель собирает файл и подтверждает целостность

#### Scenario: Несовпадение контрольной суммы

- **WHEN** собранный файл не совпадает по контрольной сумме
- **THEN** получатель отклоняет файл и не применяет его

### Requirement: Gameplay remains unreliable

Игровой ввод и снапшоты состояния MUST NOT ретранслироваться; актуальным считается только последнее отправленное состояние.

#### Scenario: Потеря ввода

- **WHEN** датаграмма с вводом потеряна
- **THEN** она не переотправляется
- **AND** следующий ввод заменяет потерянный

### Requirement: Single socket transport

Надёжный и ненадёжный трафик MUST использовать один и тот же UDP-сокет.

#### Scenario: Один порт

- **WHEN** клиент подключается к серверу
- **THEN** управляющие, файловые, игровые пакеты идут на один и тот же порт
- **AND** вторая сокет-сессия не требуется

### Requirement: Idempotent control commands

Повтор управляющей команды после ретрансмита MUST NOT приводить к повторному видимому эффекту.

#### Scenario: Повтор создания партии

- **WHEN** одна и та же команда создания партии доставляется повторно
- **THEN** создаётся ровно одна партия
