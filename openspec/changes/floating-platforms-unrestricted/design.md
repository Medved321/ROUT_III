# Design

## Context

См. `proposal.md` — Why. Текущее состояние задают in-progress changes
`floating-sector-platforms` и `floating-sector-contact`: парящая плита —
это `Sector.floating`, верх/подошва которой рисуются оверлеем
(`engine/platform_render.py`), а границы исключены из BSP/блокирующего индекса.
Валидация и редактор уже разрешают часть свободных контактов после
`floating-sector-contact`, но остаются поведенческие ограничения: LOS/hitscan/
projectiles 2D, враги не поднимаются на плиты (`allow_platforms=False`),
частично закрытый спрайт рисуется целиком (`sprite_occluded` → bool), а
некоторые операции редактора/валидации всё ещё трактуют плавающие конфигурации
как особый случай.

Ограничения: протокол big-endian, сервер авторитетный, engine не зависит от
client/server, numpy — только клиент, оптимизация не должна ломать механики.
`WORLD_STATE` уже несёт `z` игрока (v14); записи пуль в снимке `z` не несут.

## Goals / Non-Goals

**Goals:**
- Убрать искусственные ограничения плавающих платформ в данных, редакторе и
  симуляции в рамках возможностей существующей модели без прыжка/гравитации.
- Сделать плиты объёмными препятствиями для LOS/hitscan/projectiles.
- Сделать окклюзию спрайтов непрозрачной на уровне видимых колонок.
- Дать врагам использовать плиты как опору по тем же правилам шага/просвета.

**Non-Goals:**
- Прыжок, гравитация, падение, свободный полёт, 3D-навигация с pathfinding.
- Попиксельная альфа-маска спрайтов; достаточно колонкового/сканлайн-клиппинга
  по интервалам плиты.
- Изменение визуального стиля или текстурного пайплайна.

## Decisions

### 1. 3D-проверка плиты = 2D пересечение + интервал высоты

**Решение:** Для LOS/hitscan/projectile проверять плавающие сектора как объёмы:
сначала обычная 2D-проверка стен/дверей, затем проверка пересечения траектории
с проекцией плавающих секторов и сравнение высоты траектории в точке входа/выхода
с интервалом `[ceil_h, floor_h]` плиты. Для хитскана высота берётся по лучу
`z(t) = z0 + dz*t`; для LOS — линейная интерполяция между высотами глаз двух
акторов; для снаряда — текущая высота полёта снаряда.

**Альтернативы:**
- Полноценный 3D BSP/воксельный объём: слишком дорого и ломает границу текущего
  движка/карты.
- Только проверка "над/под" без объёма: не ловит попадание в бок/объём.

**Обоснование:** карта уже хранит 2D контуры и высоты секторов; `sectors_at`/
point-in-loop и существующая геометрия дают основу. Проверка остаётся
детерминированной и согласованной для трёх видов трасс.

### 2. Высота снаряда — серверное состояние пули

**Решение:** добавить серверным пулям высоту полёта (`z`) и источник высоты
(глаз стрелка/высота оружия). Блокировка плитой и попадание по цели учитывают
`z` пули и высотный диапазон цели. Если для клиентского отображения потребуется
передавать `z` в `WORLD_STATE`, это делается отдельным протокольным решением с
подъёмом `PROTOCOL_VERSION`; в рамках этого change минимально необходимый объём
— серверная авторитетная проверка.

**Альтернативы:**
- Оставить пули 2D и "притворяться" 3D только в спецслучаях: нарушает запрос и
  создаёт расхождение с LOS/hitscan.
- Сразу менять wire-формат пули: возможно, но это рискованный побочный эффект;
  нужно фиксировать только если клиенту реально нужна высота для рендера/эффектов.

**Риск:** если клиент рисует трассер/impact без z, возможен визуальный разнобой
при стрельбе над/под плитой. Проверку и эффекты нужно сверить в smoke.

### 3. Непрозрачная окклюзия спрайтов через интервалы плиты

**Решение:** использовать интервалы, уже собираемые `platform_render.draw_platforms`
(`t_near, screen_y0, screen_y1` по колонкам), как источник клиппинга. Вместо
булевого `sprite_occluded` рендер спрайта получает видимые вертикальные spans в
каждой экранной колонке и рисует только их (через area-blit/полосы). Полное
покрытие = ничего не рисовать; частичное = рисовать видимые куски.

**Альтернативы:**
- Per-pixel depth mask для каждого спрайта: точнее, но дороже и требует новый
  буфер/композицию.
- Оставить all-or-nothing: противоречит запросу "не просвечивали".

**Обоснование:** колонковый буфер глубины и интервалы плит уже существуют;
клиппинг по интервалам даёт непрозрачность без выделения больших поверхностей.

### 4. Враги используют плиты как опору

**Решение:** в `_enemy_step_ok` разрешить `allow_platforms=True` и применять те
же `support_at`/просвет правила, что игрокам. AI-поворот/наведение не меняют
модель перемещения: без прыжка/гравитации враг может подняться только на шаг
`STEP_HEIGHT`. Стопки плит проходимы, если между уровнями есть допустимые шаги
и просвет.

**Альтернативы:**
- Отдельный навигационный граф по плитам: правильно для сложных карт, но это
  большой новый подсистемный проект.
- Телепорт/автоподъём: нарушает запрет на прыжок/гравитацию.

### 5. Валидация/редактор — только проверки целостности

**Решение:** удалить топологические запреты на контакт/стопку/хост. Сохранить
проверки, которые защищают от неоднозначных данных: `MIN_PLATFORM_THICKNESS`,
валидные ссылки, обычная опора для вещи, замкнутый/интерпретируемый контур,
диапазоны высот. Редакторские операции должны давать понятный отказ только при
невозможности однозначно применить изменение.

**Альтернативы:**
- Удалить вообще все проверки: приведёт к битым картам и невалидной геометрии.
- Оставить часть запретов "на всякий случай": противоречит запросу.

## Risks / Trade-offs

- [3D projectile checks add CPU cost] → ограничить проверку плавающих секторов
  bbox/near-list кандидатов, переиспользовать существующие polygon/bbox данные;
  не вводить per-frame аллокации.
- [Bullet wire format may lack z] → начать с серверной авторитетной высоты;
  если клиентский рендер/impact потребует z, оформить отдельный version bump.
- [Column clipping can complicate sprite draw path] → реализовать через
  существующие screen-column spans и area blit, не создавать полноэкранные
  маски; сохранить fast path при отсутствии перекрытия.
- [Enemy AI may look dumb on platforms] → это приемлемо в рамках non-goal
  (нет pathfinding); важно, чтобы движение было легальным и не застревало в
  невалидной опоре.
- [Conflicts with in-progress floating-platform changes] → держать дельты в тех
  же capability paths, явно отметить зависимость в proposal/tasks и сверять при
  archive/apply.

## Migration Plan

- Обновить delta specs и применить изменение как обычный OpenSpec change.
- Старые карты с плавающими секторами остаются валидными: ограничения
  ослабляются, формат не ломается.
- При необходимости протокольного расширения для высоты пули — отдельный bump
  `PROTOCOL_VERSION` с одновременным обновлением encode/decode/tests.

## Open Questions

- Нужен ли `z` снаряда в wire-снимке для клиентского рендера трассера/impact,
  или достаточно серверной 3D-проверки и текущего 2D отображения? Это влияет на
  протокол, поэтому решить до реализации projectile-визуала.
