## Context

Секторные карты — это `SectorMap` (`shared/sector_map.py`): вершины,
линии (`LineDef`), стороны (`SideDef` upper/mid/lower), сектора
(`Sector` floor/ceil/текстуры/light/special/tag) и вещи (`Thing`).
Сериализация — `.mt1` (`shared/mt1.py`, WAD-подобный бинарный контейнер,
без зависимостей). Модель полная по полям: есть `special/tag` у линий и
секторов, `light`, списки типов вещей (`ENEMY_NAMES`/`ITEM_NAMES` в
`engine/map_editor.py`) и текстуры (`engine/textures.py`).

Что реально обрабатывается в игре сегодня: геометрия/порталы/свет
(движок), спавн игрока из `player1` (`SectorMap.spawn_px`), тайловые
двери в `map_utils`. `special/tag`, механики дверей/рычагов и вещей из
карты на сервере пока не выполняются — поля транспортируются, поведение —
резерв. Текстовый формат накрывает всю модель (полные данные),
разделяя «реализовано сейчас» и «резерв».

## Goals / Non-Goals

**Goals:**
- Человекочитаемый `.mts` (русские ключевые слова), строчный, с
  комментариями `#`, без ручных индексов сущностей.
- Автопостроение вершин/линий/сторон/секторов из «комнат по углам»;
  автоматические двусторонние грани на общих стенах.
- Полная модель механик как данных: текстуры сторон, свет, `special/tag`,
  триггеры, вещи (игрок/враги/предметы).
- Парсер и сериализатор stdlib-only в `shared/`; конвертация в `.mt1`;
  понятные русские ошибки с номерами строк.
- Round-trip: `parse(render(m))` эквивалентен `m`.

**Non-Goals:**
- Реализация серверной логики механик (открытие дверей, срабатывание
  триггеров, выдача предметов) — отдельный будущий change.
- Игровой текстовый язык сцены/логики — только статические данные карты.
- Изменение `.mt1`/протокола/движка — формат ведёт в существующую модель.

## Decisions

### D1. Расширение и место парсера
Файл карты — `.mts` (text sector). Парсер/сериализатор — в `shared/`
(новый `shared/text_map.py`), stdlib-only поверх `shared.sector_map`.
Серверу текст не нужен (принимает `.mt1`), но парсер полезен редактору,
автору и smoke-тестам; размещение в `shared` сохраняет единственный вход —
`SectorMap`.

### D2. Граф команд
Строчные команды с пробельными разделителями; параметры привязываются к
последней сущности (комната/стена/вещь). Ключевые слова: `КОМНАТА {имя}`
(открывает сектор), `угол x y`, `СТЕНА x1 y1 x2 y2`, `ИГРОК/ВРАГ/АПТЕЧКА/
ПАТРОНЫ x y [тип]`. Параметры: `пол`, `потолок`, `свет`, `пол_текстура`,
`потол_текстура`, `стена`, `текстура`, `текстура_верх`, `текстура_низ`,
`тег`, `триггер`. Регистр ключевых слов — безразлично (up-case в примерах).

### D3. Автопостроение геометрии
Вершины индексируются по точной паре координат `(x, y)` — одинаковые
координаты дают одну вершину (общие стены). Для каждой комнаты создаётся
сектор; каждая грань комнаты — кандидат в линии `(v_i, v_next)`. При первой
встрече пары -> создаётся линия с front-стороной (заполняется mid-текстура
из `стена`, upper/lower из `текстура_верх/низ`); при повторной встрече
(действител ней другая комната/СТЕНА на та же пара) — та же линия
дооружается back-стороной (двусторонняя). Ориентация: пара координат
сравнивается без учёта направления (нормализуем), порядок вершин в `LineDef`
сохраняется так, чтобы front-сектор оставался слева (совместимо с
`create_map` из `sector_map`).

### D4. `СТЕНА` — явные грани
Отдельные стены добавляются как `СТЕНА x1 y1 x2 y2 [`параметры`]`.
Они создают/переиспользуют вершины, создают сторону/механику и связываются
с соседними секторами (если внутри комнаты — front; если на общем ребре —
двусторонняя). Служат для дверей, триггеров и текстур, не заданных в
комнате.

### D5. Механики и вещи как данные
`тег N` на комнате → `Sector.tag`; `тег N` на `СТЕНА` → `LineDef.tag`;
`триггер тип ... тег N` → `LineDef.special` (код типа) + tag. Типы
кодируются маппингом русских слов («рычаг», «дверь») в numbers — таблица
в парсере, документируемая в комментарии. Вещи: `ИГРОК` → `player1`,
`ВРАГ <имя>` → `ENEMY_NAMES`-значения (`солдат`→`soldier` и т.п.),
`АПТЕЧКА`→`med`, `ПАТРОНЫ`→`amm`. Это полные данные `.mt1`; поведение —
резерв (см. Non-Goals), помечено комментарием в `render` на выходе.

### D6. Валидация и ошибки
Отдельный проход: разбираем в модель, затем `SectorMap.validate()` +
структурные проверки парсера. Сообщения — русские, с номером строки
(`строка N: ...`). Диапазоны (`свет 0..255`) проверяются при разборе.
Отсутствие `ИГРОК` ловится штатно `validate()` ("map has no player1
spawn") — переводится в понятную форму.

### D7. Round-trip и отладка
`render(SectorMap) -> str` выводит канонический текст: комнаты по секторам,
`СТЕНА` для линий вне комнат/с особенными сторонами, все вещи. Комментарием
`# формат: ROUT III .mts v1` вверху. Числа — целые (координаты редактора
целые; float округляются до .5, если не целые) — `light` и высоты целые.

## Risks / Trade-offs

- **Тексты в UTF-8/кодировках блокнота** → парсер читает UTF-8 (и BOM
  игнорируется); в кодировке Windows-1251 выдаём понятную подсказку.
- **Нумерация индексов в `.mt1` не видна автору** → автопостроение снимает
  риск «битых номеров»; валидация ловит опечатки/разрывы контуров.
- **Русские ключевые слова vs интернациональность** → осознанный выбор
  аудитории (русскоязычный автор); при необходимости — псевдонимы позже.
- **Правильная ориентация front/back** → тест на общей грани двух комнат
  (порог/проём); неверная ориентация ловится визуально в editor-примьете.
- **Механики-резерв могут «пропасть» в игре** → в `render` и парсере поля
  сохраняются полностью; будущий change лишь добавит поведение.

## Migration Plan

1. Реализовать `shared/text_map.py` (парсер/сериализатор, D1–D7) + таблицы
   типов/текстур.
2. Написать `smoke_text_map.py`: парсинг примера, round-trip,
   двусторонняя грань, ошибки («не замкнута», «свет вне 0..255»).
3. Интеграция с редактором: «Сохранить .mts»/«Открыть .mts» (импорт в
   `SectorMap`, экспорт из неё) — без изменения внутренней модели.
4. Прогнать регрессию секторных `.mt1` (код до/после парсинга карт).
5. `openspec validate --strict`.
