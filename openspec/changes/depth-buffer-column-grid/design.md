# Design

## Что именно сломано

Колоночная сетка глубин (`z_b`) раскладывается на `const.W` экранных
столбцов. У неё есть **шаг** (сколько экранных столбцов закрывает одна
колонка буфера) и **длина**. Потребителям нужны оба, и сегодня каждый берёт их
откуда может:

| Потребитель | Откуда берёт длину | Откуда берёт шаг | Буфер построен |
| --- | --- | --- | --- |
| `rendering.py:1088` (спрайты) | `const.W // SCALE` | `SCALE` | — |
| `rendering.py:1246` (глаз врага) | `const.W // SCALE` | `SCALE` | — |
| `rendering.py:1279` (боты) | `const.W // SCALE` | `SCALE` | — |
| `rendering.py:1339` (игроки) | `const.W // SCALE` | `SCALE` | — |
| `particles.py:242` (частицы) | `NC` (параметр!) | `gs.render_scale` | — |
| `rendering.py:1459` (туман) | `len(z_b)` | `SCALE` | — |
| тайловый `rendering.py:904` | `const.W // SCALE` | `SCALE` | ✅ сходится |
| секторный `sector_render.py:901` | `W // gs.render_scale` | `gs.render_scale` | ✅ сходится |

Строки со «сходится» — единственные, кто знает про буфер. Все потребители
сверху полагают, что буфер устроен как `const.W // SCALE`. Тайловый путь так и
устроен, поэтому там всё работает (и поэтому баг жил годами: тайловые карты
играются чаще). Секторный путь устроен иначе, и это молчание стоило крэша.

## Почему именно `IndexError`, а не «неверная колонка»

Индекс зажимается в `const.W // SCALE - 1`. Эта граница — **предположение о
длине буфера, зашитое в clamp**. Когда `len(z_b)` меньше, clamp не спасает: он
и есть выход за границу.

```
const.W = 1000, SCALE = 2  ->  NC = 500, граница idx = 499
gs.render_scale = 4         ->  len(z_b) = 1000 // 4 = 250
sx = 700                    ->  idx = min(499, 350) = 350  ->  z_b[350] -> IndexError
```

Существующая проверка `0 <= sx < const.W` не спасает: она про **экран**, а
выход за границу случается на **колонке буфера**.

Проверено прогоном по сетке `const.W ∈ {640, 1000, 1600, 3840} × SCALE ∈ {2, 4}
× gs.render_scale ∈ {1, 2, 3, 4, 5, 6, 8}` (56 комбинаций) на настоящем
`render()` с секторной сценой: `IndexError` в `rendering.py:1088` возникает на
20 строках — ровно на тех, где `gs.render_scale > const.SCALE`, и больше нигде.

## Решение: буфер — единственный источник истины

Длина буфера — это `len(z_b)`. Это не «настройка», которую можно вывести из
двух других настроек и ошибиться: это то, чем буфер фактически является.
Поэтому единственная честная операция — спросить у буфера его сетку:

```python
def depth_col(z_buf, sx, screen_w):
    n = len(z_buf)
    if n <= 0 or screen_w <= 0:
        return -1
    if sx < 0 or sx >= screen_w:
        return -1
    col = sx * n // screen_w
    return col if col < n else n - 1
```

Свойства, ради которых это правильная форма:

- **Не может выйти за границу.** `col < sx <= screen_w` даёт `col < n`;
  последняя строка — страховка от вырожденных `screen_w`, а не от логики.
- **Точна при любом шаге.** `sx * n // screen_w` — это ровно «умножить на
  длину, разделить на ширину», то есть в точности отображение экранного
  столбца в колонку для **любой** длины буфера, а не только для кратной
  `SCALE`. На дефолтной конфигурации (`n == screen_w // SCALE`) даёт
  `sx // SCALE` — то же самое число, что и раньше, поэтому кадр не меняется.
- **Возвращает осмысленный «нет колонки».** `-1` вместо зажатого индекса:
  зажим тестировал бы глубину соседней колонки и спрайт то исчезал бы, то
  проступал бы сквозь стену. «Нет колонки» — значит «не видно».

## Почему хелпер живёт в `framebuffer.py`

Его используют и `rendering.py`, и `particles.py`. `rendering.py` импортирует
`particles`, значит хелпер не может жить в `rendering.py` (цикл).
`particles.py` не должен импортировать `rendering.py` — и не должен. 
`framebuffer.py` — модуль про геометрию буфера кадра, зависит только от
pygame/numpy, ничего не знает ни про игру, ни про рендер, и уже входит в
разрешённый состав движка. Геометрия колонки — это ровно его предмет.

## Замороженный импорт в `sector_render`

Отдельный, независимый дефект, который маскировался крэшем.

```python
from engine.constants import W, H, TILE, TEX_W, FOV, CAM_Z   # sector_render.py:25
```

Это привязка импорта: `W`/`H`/`FOV` копируются в момент первого импорта
`engine.sector_render` (он ленивый — происходит на первом секторном кадре).
Дальше `client/renderer.py:96` пишет `const.W/const.H` на каждом ресайзе, а
`client/settings.py:367` — `const.FOV`, и модуль об этом не узнаёт.

Последствия, все без исключения:

- `render_scene()`/`bsp_clipped_frame()` (`iw = W // scale`) строят буфер для
  старой ширины и рисуют в `pygame.draw.rect(..., (0, vy, W, vh))` по старой
  ширине — то есть заливают не весь экран, если окно сузилось;
- `project_object()` (`sx = ... * W`, `sx = ... * FOV`) проецирует спрайты по
  старой ширине и старому FOV;
- `math.tan(FOV * 0.5)` (`sector_render.py:461,538`) строит лучи по старому FOV.

Ресайз окна и смена FOV — поддерживаемые возможности (`window-size-and-tractor-controls`,
`menu-hitboxes-and-text-layout`, `smoke_resolution_controls.py` проверяет
640×480 / 1000×700 / 1600×900 / 3840×2160), так что это не редкий путь.

Правка: `W`, `H`, `FOV` читаются как `const.W`, `const.H`, `const.FOV` в
момент использования. По значению остаются `TILE`, `TEX_W`, `CAM_Z` — их никто
не переприсваивает (`grep` по `const.TILE =` / `const.TEX_W =` / `const.CAM_Z =`
пуст), и копия тут безвредна. Пункт 25 перестаёт быть ловушкой.

## Про `NC` в `draw_particles`

Параметр был вторым источником истины: он передавался из `render()` как
`const.W // SCALE` и использовался как граница clamp'а — то есть ровно то
же место, где и вылезал IndexError. Оставить параметр «на всякий случай»
значит оставить рядом мину, который выглядит как рабочий. Убирается; два
вызова (`rendering.py:1442`, `smoke_perf.py:252`) обновляются.

Заодно `vh=const.H` как значение по умолчанию — тоже замороженная копия (дефолт
вычисляется в момент `def`). Меняется на `vh=None` с чтением `const.H` внутри:
`render()` всегда передаёт `_RH` явно, так что живого бага тут нет, но
сигнатура перестаёт врать.

## Туман

`fog_surf.fill(..., (i * SCALE, 0, SCALE, _RH))` — тот же дефект в третьем
месте: полоса шириной `SCALE` на колонку, привязанная к началу экрана. Когда
шаг буфера равен `SCALE`, это точно; иначе полосы съезжают, а последние
колонки (`i * SCALE + SCALE > const.W`) уезжают за край поверхности. Нужна
та же арифметика, что и `_frame_column_span(i, nc, iw)` — хелпер уже есть в
`rendering.py:83` и делает ровно `(i*iw)//nc, ((i+1)*iw)//nc`.

## Что НЕ меняется

- Число лучей/колонок в любом режиме. Тайловый буфер — по-прежнему
  `const.W // SCALE`, секторный — по-прежнему `const.W // gs.render_scale`.
  Меняется только то, как потребитель узнаёт номер колонки.
- `render_scale` в `config.json` и ладдер `client/performance.py`.
- Семантика окклюзии «`z_b[col] > dist`» — «ближе, чем стена в этой колонке».
  Меняется только то, какая колонка берётся.
- Всё, что не про глубину: `bsp-renderer-mt1-format` и `total-performance`
  этот change не трогает.
