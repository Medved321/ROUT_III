## Context

`run_client.bat`/`run_server.bat` — batch-файлы cmd.exe; на Linux они
неприменимы, а Windows-лаунчер `py` отсутствует. Существующий
`tools/bootstrap.py` умеет создавать `.venv` и ставить `requirements.txt`, но
считает, что интерпретатор уже установлен, и ищет его только среди
`py`/`python` (`PY_CANDIDATES`), чего на Linux недостаточно: во многих
дистрибутивах есть лишь `python3`, а CPython 3.12 может не быть вовсе.

`client/onboarding` уже требует автоустановки *зависимостей* (venv + pip), но не
*интерпретатора*. Новое поведение — подготовка самого CPython — и есть предмет
этого change.

## Goals / Non-Goals

**Goals:**
- `run_client.sh`/`run_server.sh` запускают игру на Linux так же надёжно, как
  `.bat` на Windows (из любого каталога, с пробросом аргументов).
- На машине без подходящего CPython first-run не требует ручных шагов: сборка
  скачивается, проверяется по `sha256` и распаковывается в пользовательский
  каталог без root.
- Повторные запуски не скачивают ничего заново.
- Ошибки (нет сети, нет загрузчика, неизвестная архитектура, битая сумма) —
  понятны и не запускают игру.

**Non-Goals:**
- Не менять Windows-`.bat` и логику venv/pip (кроме переиспользования
  `sys.executable` в `find_python()`).
- Не поддерживать musl/Alpine и архитектуры вне `x86_64`/`aarch64` gnu.
- Не устанавливать системные пакеты и не требовать `sudo`.
- Не менять игровой код, протокол, `shared/`.

## Decisions

### D1: Pinned standalone CPython 3.12.14 (python-build-standalone)

Берётся `install_only`-сборка из релиза `20260924`; URL и `sha256`
зафиксированы константами в `tools/ensure_python.sh`:

| Архитектура (`uname -m`) | Triple | sha256 |
|---|---|---|
| `x86_64` | `x86_64-unknown-linux-gnu` | `5eae8cf79dd47fc2496a4fccc892936be831ce7a84d984b2299dfb1cdb592682` |
| `aarch64` / `arm64` | `aarch64-unknown-linux-gnu` | `c0574c9c9fec561eb192ad510e4e79aaad039929b3531b3bb873e2f630fb14a9` |

URL-шаблон:
`https://github.com/astral-sh/python-build-standalone/releases/download/20260924/cpython-3.12.14%2B20260924-<triple>-install_only.tar.gz`.

_Альтернатива:_ тянуть «latest» с GitHub API — требует `jq`/парсинга JSON и
непроверяемо по `sha256`; отклонено. Pinned-значения — единственный способ
проверить целостность.

_Альтернатива:_ `apt`/`dnf`/`winget`-аналог — требует root и различается по
дистрибутивам; отклонено.

### D2: Пользовательский каталог установки

`${XDG_DATA_HOME:-$HOME/.local/share}/ROUT/python/3.12.14`, переопределяется
`ROUT_PYTHON_DIR`. Внутри — распакованное дерево сборки, интерпретатор —
`<dir>/python/bin/python3` (`install_only` кладёт всё под `python/`). Каталог
считается готовым, если `bin/python3` существует и сообщает версию 3.12;
тогда загрузка пропускается. Удаление каталога — штатный способ «сбросить»
интерпретатор.

### D3: POSIX `sh`, а не bash

Скрипты — `#!/usr/bin/env sh`. Корень проекта вычисляется без `readlink -f`
(не POSIX): `DIR=$(CDPATH= cd -- "$(dirname -- "$0")" && pwd)`. Никаких
bash-измов (`[[`, массивы, `pipefail`), чтобы работать и под `dash`.

### D4: Загрузчики и утилиты

Скачивание: `curl -fsSL -o` при наличии, иначе `wget -q -O`. Проверка суммы:
`sha256sum` (coreutils), при отсутствии — `shasum -a 256`. Распаковка: `tar xzf`
в `mktemp -d`, затем перемещение готового дерева в каталог D2. Если нет ни
`curl`, ни `wget` — понятная ошибка (Requirement «Читаемые сообщения»).

### D5: `bootstrap.py` переиспользует `sys.executable`

В `find_python()` первым кандидатом становится `sys.executable` (проверяется
тем же `_probe`: версия ≥ 3.12, не free-threaded). Это нужно, потому что лаунчер
вызывает `python3.12 tools/bootstrap.py run …`, а сам bootstrap иначе снова
искал бы `py`/`python` и падал на системе только с `python3`. Правка
безопасна для Windows: `sys.executable` уже валиден, когда bootstrap успешно
запустился.

### D6: LF и исполняемый бит

`.gitattributes`: `*.sh text eol=lf` — иначе git на Windows (при
`core.autocrlf=true`) запишет CRLF и сломает shebang. Исполняемый бит
фиксируется в индексе (`git update-index --chmod=+x run_client.sh run_server.sh
tools/ensure_python.sh`), чтобы после клонирования файлы сразу запускались.

### D7: Тестируемость без сети и без Linux

`smoke_linux_launchers.py` (как `smoke_launchers.py`) проверяет:
- наличие/формат файлов: shebang, только LF, отсутствие CRLF, исполняемость;
- ссылки на `tools/ensure_python.sh` и проброс `"$@"`;
- совпадение pinned URL/`sha256` с ожидаемыми в тесте (защита от «поехавшего»
  релиза);
- `sh -n`-синтаксис, если в системе есть `sh`/`bash` (Git Bash, WSL); иначе
  проверка помечается пропущенной, но не падает;
- выбор интерпретатора: `ensure_python.sh` с подставленным в `PATH` стабом
  `python3.12` выбирает его без загрузки; при `ROUT_PYTHON_NO_INSTALL=1` и
  пустом наборе — ненулевой код и понятное сообщение.

Реальная загрузка/распаковка в автотестах не выполняется — проверяется на
Linux вручную (WSL/VM/CI при наличии).

### D8: Отдельная capability, а не правка `client/launcher`/`client/onboarding`

`client/launcher` (Windows-`.bat`) и `client/onboarding` (venv/зависимости) —
уже неархивированные ADDED-capability; наращивать их форками дельт пришлось бы
с оглядкой на порядок архивации. Новая платформенная область (Linux + подготовка
интерпретатора) выделена в `client/linux-launcher`; существующие требования не
меняются.

## Risks / Trade-offs

- **[Pinned-хэши устаревают]** Смена релиза python-build-standalone делает URL
  недоступным. → Значения в одном месте, покрыты тестом; обновление — правка
  двух констант.
- **[glibc vs musl]** `*-unknown-linux-gnu` требует glibc; на Alpine (musl)
  собранный интерпретатор не запустится. → Вне scope; при сбое запуска
  пользователь увидит ошибку загрузки/запуска. Musl-триплет — возможное
  расширение.
- **[Объём]** Первая установка — ~65 МБ загрузки и ~200 МБ на диске. → Только
  когда Python отсутствует; каталог переиспользуется и удаляется вручную.
- **[Windows-разработка]** `.sh` не выполняются в cmd; полный прогон — под
  Git Bash/WSL/CI. → Автотесты статические + `sh -n`, реальный прогон —
  отдельная ручная задача.
- **[Полураспакованное дерево]** Обрыв распаковки может оставить мусор. →
  Распаковка в `mktemp -d`, перенос в каталог D2 только после успеха, при
  ошибке — очистка.
