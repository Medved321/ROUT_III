## Context

Текущий движок рисует 3D-сцену прямо в `gs.screen` (const.W×const.H при
`render()`), тратя кадр на по-колоночные `transform.scale`/`blit`, создание
временных `pygame.Surface` на колонку (рендер секторных сцен) и Python-циклы по
пикселям/колонкам; стоимость прямо пропорциональна размеру экрана. Бюджет FPS и
адаптивное качество заданы в ещё не заархивированных changes `client/performance`
(low-end-performance) и `renderer/sector-renderer`/`editor/sector-editor`
(advanced-sector-editor). Согласованное решение заказчика: цель — ультра-низкий
минимум сегодняшнего железа при внутреннем разрешении ~320×200; numpy — 
обязательная зависимость только клиента (сервер остаётся stdlib-only); 
оформляем отдельным change `total-performance` поверх существующих.

## Goals / Non-Goals

**Goals:**
- Фреймбуферный бэкенд: весь 3D-рендер в единый низкоразрешённый буфер,
  C-быстрые массовые операции, один upscale на кадр.
- «Хорошая графика» (текстуры стен + перспективные флаты + свет) при 60 FPS на
  эталонной слабой машине.
- Единый контроллер бюджета по всем экранным состояниям + метрики.
- Ноль регрессии тайлового/секторного рендера, редактора и лобби.

**Non-Goals:**
- 3D-физика на сервере; C-расширения; многопоточный рендер; numpy на сервере.
- Переписывание алгоритмов тайлового рендера (только перенос на бэкенд).

## Decisions

### D1. Буфер — плоский одномерный массив RGB с готовым форматом пикселей
`framebuffer.Frame` держит `bytearray` длины `IW*IH*3` (или `*4` под
`SDL_PIXELFORMAT_ARGB8888` для скорости конвертации) и вспомогательный
`memoryview`. Заполнение только массовыми операциями: срезовые присвоения
`buf[off:off+n] = bytes_`, numpy-операции работают через
`np.frombuffer(buf, np.uint8).reshape(IH, IW, 3)`. В конец кадра
`pygame.image.frombuffer(buf, (IW, IH), 'RGB')` (или прямая запись в
`pygame.Surface` через `BufferProxy` `pixels3d`-аналог) + один
`pygame.transform.scale`/`smoothscale` в `gs.screen`.
Альтернатива (по-объектный `blit` в маленькую `Surface`) отклонена: она всё
равно упирается в SDL-blit за объект и не даёт массовых операций; единый
буфер + numpy — база всего бэкенда (numpy обязателен, см. D2).

### D2. Запись флатов через numpy-индексные карты (surfarray)
Перспективный пол/потолок: для фиксированного IW×IH и горизонта заранее
считаются два массива офсетов `u_off[v]`, `v_off[v]` (по расстоянию строки),
текстурная выборка выполняется как `flat_img[np.clip(base_v+v_off,0,H-1),
np.clip(u_off+u_range,0,W-1)] * свет` — массивные операции, без циклов. numpy –
обязательная клиентская зависимость: `import numpy` выполняется на старте,
при отсутствии клиент завершается с явным сообщением (см. спецy
`client/render-backend`). Сплошная заливка по тиру «Средняя»/«Быстрая» — это
визуальная опция тира, а не замена numpy; свет везде из общей палитры уровней.

### D3. Кэш полос/спрайтов — трёхмерный кэш, ленивый и с лимитом
Кэш ключей (текстура, уровень света, бакет дальности) для стен и (тип спрайта,
уровень света, бакет дальности) для спрайтов. Бакеты дальности — геометрическая
шкала (≈ N штук, постоянное число уровней, ~16), чтобы высота полосы грубо
совпадала с проекцией, а разница с физической проекцией — не видна на 1-2 px
внутреннего буфера. Заполняется лениво при первом попадании; при превышении
лимита памяти выбрасываются самые старые (LRU) полосы. Горячий путь стены:
полоса из кэша → `blit`/срезовая вставка по колонке в буфер (1 массовая
операция на колонку).

### D4. Тайловый и секторный рендер колонок конвертируются в записи в буфер
Оба пути (`rendering.render` тайловый и `sector_render.py`) перестают блэйтить
на `gs.screen`; вместо этого каждая колонка/объект пишется в фреймбуфер:
вертикальные полосы — срезовое присваивание по колонке, спрайты/частицы —
предрасчитанные мини-спрайты. Логика высот/порталов (D4/D7 из
advanced-sector-editor) не меняется — меняется только операция записи пикселей.
Это сохраняет все требования секторного и тайлового рендера интактными.

### D5. Единый контроллер бюджета `budget.py`
`Budget` = замер `time.perf_counter` интервалов кадра + окно EMA (скользящее
среднее ~ 30 кадров) + состояние тира (auto/high/medium/fast). Решение
одно место: `budget.adapt(frame_ms)` возвращает рекомендации (тир, лимиты
отображаемых спрайтов/частиц, детали редактора); все экраны подписываются на
него. Гистерезис порогов: включение снижения при >90% бюджета устойчиво (2+
кадра), возврат при <70% устойчиво. Метрики пишутся в `gs.metrics` и в
лог-файл при включённой диагностике (<1% кадра — обновление один раз в
секунду). ВАЖНО: все рычаги контроллера — сугубо визуальные (разрешение,
освещение, число отображаемых спрайтов/частиц, детали канваса); контроллер
SHALL NOT влиять на игровое состояние (сущности мира, урон, поведение врагов,
доступность действий) — иначе это кастрирование игры (см. спецy
`client/frame-budget`, «Механики не кастрируются»).

### D6. Редактор карт под тем же бюджетом
Канвас редактора, если не влезает в бюджет: кэш сетки уже есть
(advanced-sector-editor), дополнительно срезается толщина сетки/рисования
подсветки и число вспомогательных оверлеев; панорамирование/зум — единственное,
что напрямую связано со стоимостью (инвалидация всего канваса) — при просадке
строит отложенную перерисовку кэша (одно кадровое обновление на период,
семплы не теряются). Лобби: анимированные фоны по бюджету — статичная
подложка при просадке.

### D7. Эталон диагностируется бенчмарком, а не мануально
`tools/perf_bench.py --map maps/... --seconds 30 --out results.json`: показывает
FPS, p95 длительности кадра, число адаптаций, тир; запускается на эталонной
машине до/после изменений и сверяется коммитами. Эталонная машина описана в
README (см. спецификацию § frame-budget). Сам бенчмарк не влияет на адаптацию (гасит
метрики накладку и логирование внутри замера, кроме одного итогового числа).

### D8. Бустрап запуска: автоустановка numpy
Проверка `import numpy` выполняется на старте (до pygame/меню) в отдельном
модуле бустрапа. При отсутствии numpy клиент выводит пользователю
«Установка numpy…» и вызывает `sys.executable -m pip install --user numpy`
через `subprocess` (реальный питон, запускающий zipapp; pip из окружения).
После завершения — повторный импорт; успех → обычный запуск; неудача →
явное сообщение об ошибке и корректный выход. Установка в zipapp работает,
т.к. numpy ставится в site-packages интерпретатора, а не во внутрь артефакта.
Использование `--user` снижает требования к правам; при запрете или отсутствии
сети срабатывает сценарий «Автоустановка невозможна» из спеки. Повторный
запуск уже с numpy — мгновенен
(сценарий «Установка уже произведена ранее»), никаких принудительных
переустановок.

## Risks / Trade-offs

- **numpy-флаты могут не вписаться в 16.6 мс на самом слабом эталоне при
  320×240** → снижение тира до «Средняя» (сплошные флаты) и/или внутренний
  буфер 240×150; цель «Хорошая при 60 FPS» замеряется, и если не
  достигается — фиксируем как дефект приёмки (см. спецy) и правим бэкенд, а
  не молча снижаем планку.
- **`pygame.image.frombuffer` на каждый кадр копирует буфер** → один вызов на
  кадр — приемлемо; если на эталоне копия заметна, переходим на прямую запись
  в `Surface` через `BufferProxy.get_view()` (без копии), путь выбирается
  бенчмарком.
- **LRU-кэш может расти** → лимит в байтах, фиксированный, старейшие полосы
  выкидываются; лимит зависит от тира.
- **Двойная конвертация (буфер → Surface) ломает HUD** → HUD/эффекты экрана
  рисуются после upscale на `gs.screen` (как сейчас), в буфер только
  мир-спрайты; разделение очевидно в коде.
- **Регрессия тайлового рендера** → обязательный прогон `tools/perf_bench.py`
  на тайловой карте до/после (см. спецy § frame-budget), плюс существующие
  `smoke_*.py`.
- **Лимит отображаемых спрайтов при срезе может «спрятать» важного врага**
  → рендер приоритетов: ближние/действующие сущности рисуются всегда, лимит
  применяется к далёким/декоративным; приёмка требует отсутствия «невидимых
  пуль» (см. спецy `client/render-backend`, сценарий «Враг не исчезает»).

## Migration Plan

1. Сначала `framebuffer.py` + перевод секторного/тайлового рендера через
   буфер (функционально эквивалентно, затем перф-замер — допустимы только
   улучшения или сохранение FPS).
2. numpy-флаты (обязательная клиентская зависимость) — стартовая проверка
   импорта и ясное сообщение при отсутствии; флаты + `build_client.py`
   упаковка numpy в артефакт.
3. `budget.py` + метрики; интеграция с адаптацией из low-end-performance.
4. Редактор/лобби под бюджет; `tools/perf_bench.py`; правка README (numpy
   обязателен для клиента, эталонная машина).
5. Rollback по мере необходимости: каждая стадия независима (буфер — стержневая
   инверсия; откат = revert коммита бэкенда без потери других стадий).

## Open Questions

- Битность буфера (RGB24 vs ARGB32) — выбрать по бенчмарку на эталоне; не
  влияет на спецификации (внутренний буфер ≤320×240, один upscale).
- `smoothscale` против `scale` для upscale (гладкость vs скорость) — по
  результатам бенчмарка; в «Хорошей» желателен `smoothscale`, в «Быстрой» —
  `scale`.
