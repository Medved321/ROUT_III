## Context

Сейчас карты существуют только в тайловом виде: `GameMap` (`shared/map_data.py`,
до 64×64, `~4 КБ` байт как одна дейтаграмма), редактор `MapEditorScreen` +
`TileEditor`, тайловый рендер в `client/engine/rendering.py`. Секторный рендер
`_render_sector_scene` (`rendering.py:1079`) написан, но мёртвый код: вызывает
он никогда не используется (`gs.sector_mode` всегда `False`, `sec_*` не
заполняются), а сам алгоритм наивный — на каждую колонку цикл по всем линиям два
раза, `transform.scale`+`tint`+`blit` на колонку, аллокации `pygame.Surface` на
кадр. Сервер симуляции играет строго 2D через интерфейс `GameMap`
(`is_wall_px/can_move_px/has_los_px/spawn`), вызываемый из `game_world.py` и
`weapons.py`. Мета-история: `CREATE_PARTY` (0x0A, `!IHHB`+имена) и `JOIN_ACCEPT`
(0x04, `!BHHB`) несут карту в конце полезной нагрузки и уже идут по надёжному
каналу с фрагментацией (`MAX_FRAGMENT_PAYLOAD=1000` в `reliability.py`), поэтому
размер секторной карты-JSON фрагментацией не ограничен.

## Goals / Non-Goals

**Goals:**
- Полноценная секторная модель карты, разделяемая редактором/рендером/сервером.
- Doom-style редактор и оптимизированный рендер секторных сцен уровня «DOOM 1»
  с твёрдой целью 60 FPS на машинах в два раза слабее.
- Сохранение работы тайловых карт и тайлового рендера без изменений.
- Локальная играбедность созданных карт (клиент + локальный сервер).

**Non-Goals:**
- Оптимизация/переносимость больших секторных карт по удалённой сети.
- Динамическая геометрия (лифты, платформы, анимированные двери по тегам).
- BSP вместо по-колоночной трассировки.

## Decisions

### D1. Один источник карты — `SectorMap` с тем же интерфейсом, что `GameMap`
`shared/sector_map.py`: класс `SectorMap` хранит типизированные списки
(`verts: list[tuple[float,float]]`, `linedefs: list[LineDef]`, `sidedefs`,
`sectors`, `things`) и предоставляет те же методы, что сервер уже использует у
`GameMap`: `is_wall_px`, `can_move_px`, `has_los_px`, `spawn_px` (см. D2), плюс
новые `find_sector_at`, `validate` (список ошибок), `to_json/from_json`,
`to_bytes (json)/decode`. Игровая логика и симуляция не получают веток «если
секторная» — только общей интерфейс. Альтернатива «отдельный интерфейс и
адаптеры» отклонена: кода симуляции мало, а унификация убирает дублирование.

### D2. Столкновения — полигональный тест «точка на границе сегмента»
Растеризация границ в 64px-клетки даёт ту же сложность, что тайлы, но теряет
точность на длинных лайндефах в «километровых» секторах. Вместо неё:
`can_move_px` проверяет круг радиуса `r` против ближних одно-сторонних
лайндефов (расстояние от точки до сегмента), выбирая кандидатов через
минимальный пространственный индекс (сетка с ячейкой 64px по центру-длинной
линии), маркированный как в D3. `has_los_px` — пересечение отрезка с
сегментами (случай, когда сегмент просвечивается двусторонними границами,
учитывается: проходятся только одно-сторонние). 2D-физика на сервере остаётся
неизменной.

### D3. Индекс линий для рендера и физики — сетка + штамп
Ядро: сетка ячеек размером `TILE=64` пикселей, в каждой — список лайндефов,
которые её пересекают (строится один раз при загрузке карты; сегмент в
ячейку попадает, если его bounding box пересекает ячейку). Для луча
используется тот же пошаговый обход клеток, что в тайловом рендере
(`const.TILE`), но вместо проверки «тайл — стена» проверяются только линии
ячейки. Чтобы не проверять длинную линию в каждой ячейке, вводится массив
штампов `li_last_checked[line_id] = текущий_номер_колонки` — линия
проверяется максимум раз в колонку). Это даёт O(посещённых ячеек × линии_ячейки)
вместо O(всех линий) на колонку — главный прирост скорости на больших картах.
Для физики аналогичный штамп по тику.

### D4. Порталы по-колоночно с верхним/нижним клиппингом
Для каждой колонки ведём `clip_top[i]`, `clip_bottom[i]` (как `ceilingclip/
floorclip` в DOOM). Алгоритм колонки:
1. DDA-проход по ячейкам индекса D3 до первого пересечения луча с линией.
2. Если линия одно-сторонняя — рисуем сплошной прямоугольник «пол→потолок»
   сектора передней стороны, занимаем всю колонку, стоп.
3. Если двусторонняя — считаем перепады высот: нижняя кромка (если пол заднего
   выше), верхняя кромка (если потолок заднего ниже), рисуем эти полосы,
   обновляем клиппинг, и продолжаем DDA от точки пересечения уже из заднего
   сектора, до исчерпания `view_dist` или полного закрытия колонки.
Ограничение числа продлений на колонку (например 8) защищает от циклов.
Пол/потолок рисуем только там, где `clip_top[i] < clip_bottom[i]` (закраска
целыми строками через `pygame.draw.line`, а не попиксельно).

### D5. Свет — палитра предрассчитанных уровней вместо тонировки
При загрузке карты в кэш строятся по 16 градаций каждой текстуры (через
`fill`+`BLEND_RGB_MULT` один раз, а не на кадр) — по сути «палитра DOOM».
Колонка рисуется `blit` заранее порезанной текстуры на выбранной градации.
Убирает `transform.scale`+`tint`+`blit` тройку текущего кода. Кэш строится
лениво (по имени текстуры при первом использовании) в `client/engine/
sector_render.py`, живёт в `gs`. Альтернатива «инверсная цветокоррекция на
кадр» отклонена: аллокации на кадр.

### D6. Рендер во внутренний буфер малого разрешения + один upscale
Сцена рисуется во внутренний `Surface` шириной `I_W = const.W // render_scale`
и высотой `I_H = const.H // vs_scale` (vs_scale — новый параметр качества,
порядка 3; итог ~ 1110×233 на слабом железе), затем `pygame.transform.scale`
на `gs.screen` один раз на кадр. Стены: полоса текстуры `1×TEX_W` масштабируется
в `1×(wb−wt)` (дешёво, площадь мала) и блэйтится. Спрайты/частицы/корпуса
проецируются относительно внутреннего буфера, привязка к полу сектора
(существующий путь `draw_corpse` и спрайт-рендер адаптируются через общий
хелпер проекции). HUD/прицел рисуются поверх уже на полном разрешении (после
upscale). Это и есть «разрешение 320×200 из DOOM» в нашей реализации.

### D7. Флаты — перспективная текстура по уровням, с фолбэком
Текстурированные флаты: для каждой строки внутреннего буфера между
`clip_top`/`clip_bottom` вычисляется дистанция и мировые координаты начала
строки, выбирается предрассчитанная строка флат-текстуры (кэш 16×16 уровней,
хранение в виде `bytes`/`bytearray` строк), заполнение через `bytes[::step]`
(C-скорость). На слабом железе/превышении бюджета — сплошная заливка цветом
сектора с уровнем света (текущее поведение, но с клиппингом D4). Переключение —
по адаптивному бюджету D9.

### D8. Редактор — новая модель + экран, с кэшем и пакетной отрисовкой
- `client/engine/sector_editor.py`: модель (`SectorEditor`) с операциями
  (вершины/линии/сектора/вещи/спецэффекты/теги), привязкой к сетке,
  стеком undo (поиск по снапшоту изменённых сущностей, не полной копии карты
  на каждое действие — карта хранится целиком, а на отмену сохраняется diff).
- `client/sector_editor_screen.py`: экран по образцу `MapEditorScreen` (те же
  цвета/шрифты/раскладка), с левой канвой и правой панелью: палитры
  текстур/флатов/вещей, свойства выделенного, кнопки инструментов.
  Отрисовка: фон-сетка кэшируется в `Surface` (пересоздаётся только при изменении
  зума/панорамы), лайндефы рисуются пакетно `pygame.draw.lines` по группам
  (одно-сторонние / двусторонние / выделенные-своим цветом), отсечение по
  bounding box видимой области, инвалидация только задетых прямоугольников.
  Размещение вещей — отдельный режим «Вещи» (выбор типа из палитры врагов
  `ENEMY_NAMES` / предметов `ITEM_NAMES` / `player1` / `exit`, клик по канвасу
  в пределах сектора, ПКМ — удалить), вещь рисуется условным значком/цветом
  в 2D и несёт тип/угол/координаты в свойствах.
  Палитры вещей/врагов/предметов используют `map_editor.ENEMY_NAMES/ITEM_NAMES`.
- Доступ: в лобби `E` → экран редактора карт; внутри — переключатель
  «Тайлы/Сектора» в шапке. Тайловый редактор остаётся; `MapEditorScreen.to_game_map`
  сохранён.
- «▶ Играть» (F5): валидация → сохранение в `maps/*.json` → возврат «play»
  (клиент создаёт партию как сейчас, но с секторным форматом).

### D9. Бюджет 60 FPS по всей игре — интегрируем в механизм `low-end-performance`
Новые рычаги качества секторного рендера (vs_scale, уровень флатов, уровень
спрайтов) добавляются в тот же адаптивный контроллер, что и `render_scale`
(см. `client/performance`): замер длительности кадра → при переборе бюджета
повышаем `render_scale`/`vs_scale` и срезаем флаты до сплошных, при запасе —
возврат. В редакторе — самостоятельный мягкий контроллер (если кадр канваса
дольше бюджета — переходим на перерисовку только задетых областей и
понижаем толщину сетки/Деталей). Твёрдое требование: ни одна ветка (тайлы,
сектора, редактор) не должна регрессировать FPS ниже целевого.

### D10. Протокол — байт формата карты
- `encode_create_party_ex` — заголовок `!IHHBB` (request_id, w, h, has_map,
  map_format); `decode_*` симметрично. Для сектора `map_data = json_bytes`.
- `JOIN_ACCEPT` — `!BHHBB` (pid, w, h, has_map, map_format).
- `PROTOCOL_VERSION` в `shared/version.py` поднять; `SPEC.md` — секция про
  форматы карт. Устаревшие значения w/h для сектора не значат (JSON несёт
  геометрию; w/h=0).
- Сервер: `validate_network(...)` заменяется на диспетчер по формату
  (`optional_sector`), при ошибке — log + default map, как сейчас.
- Клиент: `lobby_screen` показывает тип карты партии (тайлы/сектора) по флагу
  в `JOIN_ACCEPT` (или по имени карты), `client.py` при создании партии с
  секторной картой кодирует формат `1`.

### D11. Конвертер тайлов → сектора — подключение компонент для «старых карт»
`from_tiles(game_map)`: пустые связные области (BFS) → сектора, внешние/внутр.
стены → одно-сторонние линии, высоты 0/128, флаты/textures «по умолчанию»,
`player1` в центр каждой области. Валидность гарантируется по D-модели.
Конвертер сохраняется в модель (`map/sector-format`), вызывается из редактора
(кнопка «Импорт тайлов»).

## Risks / Trade-offs

- **Производительность Python-лучей на очень больших картах** → индекс D3 +
  штампы + понижение внутреннего разрешения (D6) дают запас; пол с потолком
  остаются узким местом — фолбэк D7 (сплошная заливка) и vs_scale. Ставим
  измеримую цель на эталонной слабой машине.
- **Перспективные флаты в Python могут не уложиться в 16.6 мс даже на
  внутреннем буфере** → многоуровневый фолбэк (текстура → плоская заливка) и
  адаптивное срезание D9; требование Tекстурных флатов в спецификации мягкое
  (переключение по бюджету).
- **Валидность произвольно рисуемых контуров** → валидация перед сохранением/
  запуском + авто-замыкание при «создать сектор из контура»; двери/спецэффекты
  простого вида (закрытая дверь) без динамики в этом change.
- **Ошибочный формат protocol (старые клиенты)** → подъём `PROTOCOL_VERSION`
  и отдельный байт формата; старые клиенты честно отклоняются по версии
  (это и есть миграция: новый сервер несовместим со старым клиентом, а новый
  клиент — со старым сервером).
- **Проблема общей линии между двумя секторами на рендере (т.н. «door crack
  seam»)** → клиппинг по-колоночно с точным проекционированием вершин убирает
  видимые швы; наложение выравнивается по `tex_u` через координату вдоль
  линии, а не по мировому `x`.

## Migration Plan

1. Добавить `SectorMap` + конвертер + формат (D1, D10) — без влияния на действующие
   партии (новая версия кода уже несовместима со старыми клиентами, поднимаем версию).
2. Развернуть секторный рендер (D3–D7) и редактор (D8) на клиенте; тайловые
   карты не трогаются.
3. Сервер: валидация/физика (D2, D10) — пути по интерфейсу `GameMap`
   сохраняются, добавление ветки для `SectorMap`.
4. Смок-тесты (см. tasks) по секторному пути; rollback = откат коммитов с
   поднятой `PROTOCOL_VERSION` (в паре).

## Open Questions

- Тип дверей/спецэффектов для первого релиза: закрытая дверь как «прозрачная
  секция» — пока не решено, делать ли визуально открывающуюся (2-3 секции).
  Не влияет на спецификации на уровне формата (тег и спецэффект
  сохраняются/редактируются), только на задачи рендера дверей. Принятый
  минимум: двери рендерятся как закрытая секция без анимации.
- Готовность влить секторные карты в протокол без оптимизации сети больших
  карт — принято для локальной игры; финальное решение по срокам сетевой
  части отдельное изменение.
