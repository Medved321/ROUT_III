# Design

## Контекст

Три подсистемы, которые встречаются в этой фиче:

| подсистема | где | частота |
| --- | --- | --- |
| `state == 3` в снимке мира | `client/network_client.py` → `client/client.py` | 20 Гц (снимки) |
| `RenderBridge.update()` | `client/bridge.py` | каждый кадр |
| `engine.rendering.render()` | `engine/rendering.py` | каждый кадр |

Ключевое ограничение: **частота у всех трёх разная**, а эффект должен
выглядеть одинаково при 30 и 240 FPS. Отсюда все решения ниже.

## Решения

### 1. Фронт по авторитетному `state`, не по интерполяции

`RenderBridge.update()` вызывается каждый кадр, а `state` меняется только в
снимках 20 Гц. Значит наивный `if state == 3: spawn(...)` будет спавнить
частицы 15 раз за один дэш.

Выбран детект **фронта** с памятью на игрока:

```
прыжок 0 -> 3:  вспышка + сброс накопителя пути
state == 3:     след, порция на каждые DASH_FX_TRAIL_PX пройденного пути
спад 3 -> 0:    сброс накопителя (чтобы следующий дэш не «продолжил» след)
```

Удаление записи при спаде важно: без него битый/пропущенный снимок оставил бы
запись в состоянии «дэширует» навсегда.

**Почему авторитетный снимок, а не интерполированный список.** Позиции чужих
игроков интерполируются с задержкой (`INTERP_DELAY`) и берутся из снимка, который
*позже* целевого времени; `state` в интерполированной записи берётся из
`st1` — то есть он тоже сдвинут. Для позиции это правильно, для фронта эффекта
это значит лишний рывок тайминга. Проще и честнее читать фронт из
авторитетного `latest` и рисовать эффект с той же задержкой, что и сама ходьба
(её и так нет — клиент не предсказывает позицию).

**Локальный игрок.** Сейчас в `RenderBridge` уходят только `other_players` —
себя клиент не рисует. Поэтому `client.py` запоминает `state` локального
игрока из того же авторитетного снимка и передаёт его отдельным аргументом
`local_state`. Никакого оптимизма: вспышка приходит тогда же, когда сервер
подтвердил дэш, то есть ровно тогда, когда игрок начинает двигаться. Без
этого локальный игрок вообще не получил бы эффекта, а «притворяться» вводом
значило бы рисовать вспышку на отказ сервера.

### 2. След по расстоянию, а не по времени

Дэш — 24 px за тик, ровно 120 px за 5 тиков. Порция на каждые
`DASH_FX_TRAIL_PX` (~26 px) даёт ~4 порции на дэш независимо от FPS. Если бы
след шёл по кадрам, то на 240 FPS клубов было бы вчетверо больше, чем на 60, а
на 30 — вчетверо меньше; хуже, на дэше в стену (позиция не меняется) появились
бы клубы на месте.

Направление порции берётся из **смещения позиции между кадрами**, а не из
взгляда: у инерполяции смещение всегда в сторону движения, у локального
игрока — в сторону дэша, и отдельно знать направление дэша нигде не нужно.
Пыль летит против движения (это то, что читается как «сорвавшийся рывок»).

### 3. Отдельный спавн, а не `spawn_particles`

`spawn_particles()` масштабирует количество через `gs.blood_amount` — это
настройка gore для попаданий. След дэша не должен исчезать, когда кровь
выключена, поэтому у него свой спавн. Общее у них только одно: лимит
`_effect_limit(MAX_PARTICLES)`. Спавн не аллоцирует ничего, кроме словаря, и
полностью переиспользует существующую отрисовку дыма (`smoke=True` → кэш
поверхности, без `pygame.draw` на частицу).

### 4. `gs.dash_fx` как затухающая огибающая

Снимки 20 Гц, дэш 250 мс — сервер может прислать `state = 3` один-два раза, а
эффект должен длиться весь рывок. Поэтому огибающая заводится в
`engine.game_state` как float и гасится **в рендере** по кадрам: рендер — уже
покадровый тик движка, он двигает `w_tmr`, `bob` и карту исследованного, так
что затухание здесь на своём месте и не зависит от того, кто вызывает
`render()`.

Полосы рисуются только пока `gs.dash_fx > 0`, то есть в покое цена нулевая.

### 5. Полосы: экранное пространство, после тумана, до HUD

`draw_dash_streaks()` рисует прямо в `gs.screen`:

- **позиция** — между дистанционным туманом и блоком HUD. Тогда полосы лежат
  поверх мира, но не закрывают ни прицел, ни лицо, ни статистику, ни оружие:
  читаемость индикаторов важнее «кинематографичности».
- **поверхность** — одна модульная `SRCALPHA`-поверхность, переиспользуемая
  между кадрами (`fill((0,0,0,0))` — это memset). Выделять новую
  полноэкранную поверхность каждый кадр нельзя: при 1000x700 это ~2.8 МБ
  аллокации на кадр (такой паттерн есть у тумана, но добавлять второй смысла
  нет).
- **таблица** — позиции/длины/толщины полос считаются один раз при импорте,
  в кадре остаётся масштабирование альфы и блит. Нет ни RNG, ни цикла по
  пикселям.
- **плотность у краёв** — y-координаты разнесены к верхнему и нижнему краю
  (по экрану движется периферия), а центр почти пустой. Это дешёвый способ
  получить радиальный «туннельный» вид, а не полосы поперёк всего экрана.
- **количество** — масштабируется `gs.effects_factor` (качество), но с
  минимумом: на низком качестве полосы остаются, иначе игрок теряет
  единственный экранный сигнал дэша.

### 6. Старение эффектов: драйвер в рендере

`update_particles`/`update_decals`/`update_weather` — парные функции к
`draw_particles`/`draw_decals`/`draw_weather`, и ни одна из `update_*` не была
вызвана. Спавн живёт в `client/bridge.py` (клиент — единственное место, где
решается, «попало ли»), но шаг продвижения — это тик движка.

Решение: вызвать все три в `engine.rendering.render()` непосредственно перед
отрисовкой эффектов. Тогда любой потребитель `render()` (клиент, replay,
smoke-тесты движка) получает корректные эффекты, а граница движка не
нарушается — модуль не знает ни про клиент, ни про сеть.

Проверка «забивается ли пул» обязательна для этого пункта: без неё тест на
`MAX_PARTICLES` проходит и на сломанном коде (тест просто не набирает 200
частиц).

## Альтернативы, отклонённые

| вариант | почему нет |
| --- | --- |
| Оптимистичная вспышка по локальному нажатию | мигает при отказе сервера (кулдаун, нет ввода движения) — эффект врёт |
| Фронт по интерполированному состоянию | фронт сдвинут на `INTERP_DELAY` относительно позиции, тайминг «плывёт» |
| След по кадрам | зависит от FPS, на дэше в стену сыпет пыль на месте |
| Переиспользовать `spawn_particles` | зависит от `gs.blood_amount`, слепота настройки gore |
| Своя отрисовка полос в `client/renderer.py` | HUD-оверлей рисуется поверх движкового экрана, полосы оказались бы под прицелом и лицом |
| Новый флаг в протоколе | `state = 3` уже несёт всю информацию, версию поднимать незачем |
| Отдельная alpha-поверхность на кадр | ~2.8 МБ аллокации на кадр ради эффекта длиной 250 мс |

## Риски

- **Починка старения меняет все эффекты сразу.** Частицы начнут исчезать по
  TTL, декали — истлевать, погода — падать. Это и есть задуманное поведение
  (иначе `life`/`alpha`/ttl в коде бессмысленны), но эффект будет виден сразу
  после первого выстрела.
- **Пул при высоком темпе стрельбы.** Если спавн успевает заполнить пул быстрее,
  чем `update_particles` его чистит, старые частицы вытесняются новыми — это
  ровно то поведение, ради которого лимит и существует, пороги не нужны.
- **Полосы на очень широком экране** при `effects_factor = 0` остаются
  минимальными (4 полосы) — намеренно: это единственный экранный сигнал дэша.
