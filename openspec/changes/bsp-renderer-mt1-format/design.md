## Context

Секторные карты существуют в виде `SectorMap` (`shared/sector_map.py`) с
JSON-сериализацией (`"format": "sector"`, `version: 1`, `to_bytes` = JSON).
Рендер секторных сцен (`client/engine/sector_render.py`) — по-колоночная
DDA-трассировка с порталами (индекс линий 64px, штампы, `MAX_PORTAL=8`),
флаты — numpy-растеризация или сплошная заливка, свет — 16 градаций, вывод
через единый фреймбуфер `gs.frame` + один upscale (из `total-performance`).
`PROTOCOL_VERSION=5`, формат карты в протоколе — байт `map_format` (0 —
тайлы, 1 — секторный JSON). Размер секторной карты ограничен
`MAX_SECTOR_BYTES=1_048_576`, фрагментация надёжного канала есть.

Целевой подход — классика DOOM 1: BSP-дерево даёт готовый порядок отрисовки,
клиппинг по колонкам, visplane-спаны флатов, colormap-свет; а .wad-подобный
бинарный контейнер `.mt1` заменяет JSON и несёт предрассчитанную BSP-структуру.

## Goals / Non-Goals

**Goals:**
- BSP-рендер секторных сцен уровня оптимизации DOOM 1 (back-to-front,
  клиппинг, visplane, colormap) с сохранением бюджета/тиров `total-performance`.
- Бинарный формат `.mt1` в стиле `.wad` (заголовок + каталог срезов) с
  точным round-trip и предрассчитанными BSP-срезами.
- Без регрессий: тайловые карты и тайловый рендер не меняются.

**Non-Goals:**
- Динамическая геометрия (лифты, платформы, анимированные двери).
- Портал-стыки нового рода, не сводимые к верхней/нижней текстуре и клипу
  (вложенность «в проёме» решается обходом BSP, а не рекурсией лучей).
- Серверное построение BSP или использование BSP-срезов в симуляции
  (сервер остаётся 2D-физикой по одно-сторонним линиям, stdlib-only).

## Decisions

### D1. `.mt1` — WAD-подобный контейнер: заголовок + каталог + срезы
Структура файла (big-endian, как весь протокол проекта):
- Заголовок: магия `b"MT1\x00"`, `u16` версия формата, `u32` число срезов,
  `u32` смещение каталога, `u32` контрольная сумма содержимого.
- Каталог: `u32`×число_срезов записей {`u32` смещение, `u32` размер,
  `8s` имя среза (ASCII, NUL-padded)}, как в `.wad`.
- Срезы после каталога: `VERTEXES` (f32 x,y), `LINEDEFS` (u32 v1,v2 + u16
  flags/special/tag + u32 front/back), `SIDEDEFS` (имена u32 idx в `NAMES` +
  смещения + u32 sector), `SECTORS` (i16 floor/ceil + u32 floor/ceil idx +
  u16 light/special/tag), `THINGS` (f32 x,y + u32 type idx + u16 angle +
  f32 z), `NAMES` (u16 число строк + строки len-prefixed UTF-8),
  `SEGS/SUBSECTORS/NODES/REJECT`.
- `to_bytes/from_bytes` секторных карт переходят на `.mt1`; JSON путь
  остаётся только как импорт старых карт (формат `"sector"`), потому что
  срезы исходной геометрии и BSP плотно соответствуют модели, а размер
  JSON-карты уже упирался в лимиты. Числа — нативные Python-типы в
  `sector_map.py` (f32 точно хранит координаты из редактора).

### D2. BSP строится один раз при загрузке и кэшируется (или берётся из файла)
Срезы `SEGS/SUBSECTORS/NODES` — предрассчитанная структура. Если карта
(полученная по сети) не несёт BSP-срезов, клиент строит BSP при загрузке
однократно и кэширует (вливается в `SectorScene`). Сервер никогда не строит
BSP — ему нужны только исходные срезы и валидация. Файл `.mt1` из редактора
пишет BSP-срезы сразу, чтобы клиент не пересобирал дерево.

### D3. BSP: рекурсивная бинарная партиция по линиям, подсекции = выпуклые полигоны
Классический алгоритм DOOM-нодбилдеров: на каждом шаге выбираем
разделитель-линию (эвристика: максимальная сумма длин по обеим сторонам,
минимум расщеплений, предпочтение линий с наименьшим рasщеплением),
расщепляем пересекающиеся линии, помечаем стороны как front/back, рекурсия
до выпуклых полигонов. Подсекция = список сегментов (выпуклый контур),
узел = разделитель + bbox-ы обеих частей. Без bbox САМО-чатных карт не
выходим за рамки: лимиты линий/сегментов уже есть. На этапе рендера bbox
узлов дают раннее отсечение (visible-frustum cull).

### D4. Рендер: обход дерева + клиппинг колонок (как drawsegs/ceilingclip в DOOM)
Кадр: от корня, на каждом узле определяем, по какую сторону разделителя
точка зрения; идём сначала в СВОЁ (ближнее) поддерево, потом в «другое»
(дальнее) — как `R_RenderBSPNode` в DOOM. Лист — подсекция: проецируем её
сегменты, для каждого вычисляем ранги колонок внутреннего буфера и
вертикальные границы (по секторам front/back и перепадам высот: верхние/
нижние кромки, mid), клиппим интервалами колонок (`clip_top[i]/clip_bot[i]`,
как `ceilingclip/floorclip`), рисуем стену полосами текстур из кэша
(`wallcache`, бакеты по расстоянию — уже есть), обновляем клиппинг: solid
закрывает колонку, двухсторонняя линия сужает клип до нижней кромки кромки /
верхней кромки пола. Так «окно/ступень» получаются штатно: двухсторонняя
линия рисует только верх/низ кромки, проём прозрачен, а стенки за ним
рисуются уже с учётом клипа ближних колонок (закрытые колонки вовсе не
затрагиваются). MAX_PORTAL-ограничение и рекурсия лучей
исчезают — порядок и клипы гарантируют дерево. Решение near-first принято
при реализации 4.2 (архитектура DOOM совместима со сценариями клиппинга и
отбрасывания сегментов из `sector-renderer`; исходный far-first вариант
несовместим с «рисовать только в видимую часть колонок»).

### D5. Флаты через visplane: спаны между клипами колонок
Флаты как в `sector_render.py` сейчас, но источник спанов — вертикальные
клипы колонок (видимая часть подсекции), а не след луча. Группируем спаны
соседних колонок с одинаковой подсекцией в один прямоугольный регион
(visplane-спан) и растеризуем перспективно numpy-массивом (или сплошной
заливкой на фолбэке). Свет и привязка — из уровня/текстуры подсекции.
Это сохраняет «Один upscale за кадр» и бюджеты флатов из `total-performance`.

### D6. Colormap-свет и кэш полос не меняются
Свет 16 градаций и `bucket`-кэш полос стен (`wallcache.DEFAULT_CACHE`)
остаются как есть — они уже реализуют colormap DOOM. BSP-путь рендера
рисует линии через те же полосы (текстура × свет × бакет), просто заказ
не «поперёк колонок DDA», а «по видимым подсекциям».

### D7. REJECT-таблица ускоряет `has_los_px`, не меняя семантики
`REJECT` — битовая матрица пар секторов «сектор A неожиданно не виден из
B» (по общности bbox/пересечения). `has_los_px` сначала проверяет REJECT:
бит установлен → сразу False без пересечений сегментов. Сервер строит
REJECT лениво при загрузке карты (чистый Python, stdlib). Семантика
симуляции не меняется — это pure-ускорение; неверный бит допускается
только в сторону «ложного непрозрачного» (консервативно), и проверяется
валидацией.

### D8. Один источник данных рендера — `SectorScene` остаётся
`SectorScene.` хранит плоские массивы линий/секторов; добавляем
`bsp: BspTree` (подсекции/сегменты/узлы/bbox). `render_scene` сигнатура и
возврат zbuffer (`view_buf`) сохраняются, чтобы спрайты/корпуса
проецировались тем же путём. Старый DDA-путь удаляем (вытеснен BSP), но
индекс линий `LineIndex` остаётся для физики редактора? Нет — физика на
сервере своя (`_ensure_index`), а `LineIndex` в рендере удалить.

### D9. Протокол: `map_format=1` → байты `.mt1`
`native`: `encode/decode_create_party_ex` несут `map_format` (0 тайлы; 1 —
сектор), `map_data` секторной карты = байты `.mt1`. `PROTOCOL_VERSION`
поднять. `validate_network` на сервере → `SectorMap.from_bytes` (mt1) +
`validate`. Старые JSON-байты как вход отклоняются по версии протокола.

## Risks / Trade-offs

- **Качество BSP (глубина, число расщеплений) влияет на FPS** → эвристика
  выбора разделителя (минимум расщеплений), ограничение глубины/числа
  сегментов; регенерация BSP при редактировании карты в редакторе (дельта).
- **Сборка BSP в Python на большой карте может быть дорогой** → один раз при
  загрузке + кэш; файлы `.mt1` уже несут готовые срезы; сервер не строит.
- **Перспективные флаты — узкое место** → visplane-спаны (меньше отдельных
  заливок, чем по-колоночные), фолбэк на сплошную заливку и адаптивная
  срезка по бюджету (риски из `total-performance` переносятся).
- **Ошибки порядка в BSP дают видимые артефакты** → валидация согласованности
  срезов перед использованием (D0 спеки sector-format) + юнит-тесты обхода
  на картах с окнами/ступенями.
- **Точность f32 координат в срезах** → хватает для пиксельных координат
  редактора (лимит координат < 2^24), при переполнении — валидация.

## Migration Plan

1. Добавить `shared/mt1.py` (контейнер/enco/de) и перевести `SectorMap`
   `to_bytes/from_bytes/load/save` на `.mt1`; JSON-импорт остаётся. Поднять
   `PROTOCOL_VERSION`. (Клиент и сервер обновляются в паре — старые клиенты
   честно отклоняются.)
2. BSP-билдер (в `client/engine/bsp.py` или `shared/bsp.py` stdlib в
   зависимости от использования) + кэш в `SectorScene`.
3. Заменить `render_scene` в `sector_render.py` на BSP-обход; вернуть
   zbuffer для спрайтов; удалить DDA-путь и `LineIndex`.
4. REJECT на сервере для `has_los_px`.
5. Редактор: сохранение в `maps/*.mt1`, импорт `.json`.
6. Смок-тесты (`smoke_mt1_*.py`, `smoke_bsp_*.py`), регрессия тайловых,
   замер 60 FPS; rollback = откат коммитов с поднятой `PROTOCOL_VERSION`
   (клиент и сервер вместе).
