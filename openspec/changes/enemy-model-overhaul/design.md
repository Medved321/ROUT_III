## Context

Текущее состояние — не «плохая картинка», а разорванный контур:

- `engine/rendering.py:414-1203` — `draw_enemy_sprite`: 19 `if/elif`-веток
  (по одной на тип), каждая рисует примитивы прямо на `gs.screen` (экранное
  разрешение, уже после `transform.scale` буфера). `healer` и `artillery`
  присутствуют в `ENEMY_DB` (`engine/constants.py:341-342`) и в пулах спавна
  (`:355-358`), но не имеют ветки — рисуются тень + HP-бар.
- `draw_corpse` (`:1205-1250`) покрывает 7 типов отдельно и 8 через общий
  эллипс; `boss_baron`, `boss_cyber`, `boss_spider`, `healer`,
  `artillery` корпуса не имеют.
- Четыре per-frame `Surface` на врага: тень (`:446`), оглушение (`:1147`),
  вспышка урона (`:1158`), свечение (`:1170`), плюс две 8×8 на «глаза в
  темноте» (`:1188`) — всё в `try/except BLEND_ALPHA_SDL2`.
- Ракурса нет: `pa` в снапшоте есть, но в отрисовке не читается.
- `engine/quality.py:12-26` содержит `sprite_ratio` / `effect_ratio` /
  `detail_ratio` с нулевым числом потребителей — тир не влияет на врагов.
- `engine/sprite_cache.py` готов (баеты дальности из `engine/wallcache.py`,
  запекание света, LRU по байтам, `Frame.blit_mini` как одна вставка), но
  **не вызывается ниоткуда**; `set_view` не вызывается никогда, поэтому
  `_edges` навсегда равен `bucket_edges(900.0)`. Две отдельные проблемы в
  нём: `mini()` всегда возвращает **квадрат** `size × size` (боссы и манкубы
  искажаются или получают пустые поля), и кэш не вызывается при смене карты.
- `engine/sprites.py:get_enemy_surface` и `client/sprite_factory.py:get_enemy_surface`
  — второй, полностью мёртвый путь enemy-арта (10 типов, квадратные
  поверхности, свой `FRAME_CACHE`). `engine/rendering.py:184-193`
  (`_ENEMY_SPRITE_MAP`) — третий, тоже не используемый.
- `client/sprite_factory.py:get_bot_surface` — рабочий образец: параметрическая
  генерация + `FRAME_CACHE` по полному ключу, подключённая через
  `gs.sprite_provider` (`engine/game_state.py:155`).

Ограничения: движок `engine/` — самостоятельный пакет (13 модулей), он не
знает о `client.*`; единственная точка входа контента — слоты в
`engine/game_state.py`. Протокол менять нельзя без смены
`PROTOCOL_VERSION` и автообновления клиента — в этом change протокол
трогать нельзя. Сервер stdlib-only.

Решения пользователя: арт процедурный, в коде (без PNG-ассетов); 8 ракурсов
billboard; объём — «визуал + баланс/поведение».

## Goals / Non-Goals

**Goals:**

- Один путь enemy-арта: дескриптор → построитель → кэш поверхностей →
  вставка в экранный буфер `gs.screen`.
- Покрытие 20/20 типов протокола, включая `healer` и `artillery`, плюс
  корпуса для всех типов и осмысленный фолбэк для неизвестного типа.
- 8 ракурсов из `pa` без изменений протокола.
- Ноль новых `Surface` на кадр в пути врага.
- Тир качества меняет детализацию модели, а не число сущностей.
- Уборка трёх мёртвых путей enemy-арта, чтобы следующий change не
  наследовал четыре источника правды.

**Non-Goals:**

- Кэш моделей в буфере для ботов, игроков, предметов, бочек, порталов и
  пуль — только враги и их корпуса (остальное — существующий
  `total-performance`).
- Спрайты из PNG-ассетов, сжатие, LOD-сетки, скелетная анимация.
- Изменение чисел `ENEMY_DB` (hp/spd/dmg) и серверной логики.
- Замена `get_bot_surface` и провайдера ботов — они остаются как есть.
- Стык с `client/render-backend` (см. ниже).

## Стык с total-performance

`client/render-backend` живёт в открытом change `total-performance`, а не в
`openspec/specs/`, поэтому дельты здесь нет. Этот change делает
требования «Кэши предрасчитанных полос и спрайтов» и «Спрайты и эффекты в
буферном бэкенде» **исполняемыми для врагов** — это их фактическое
выполнение, а не изменение формулировок. Пункт 1.4/2.3 в `tasks.md` того
change сейчас помечены `[x]`, хотя кэш не подключён: после этого change они
станут правдой. Дополнительно закрывается живой пункт «Быстрая» =
«минимум спрайтов и эффектов»: раньше тир не влиял на врагов вообще, теперь
через `detail_ratio`.

## Decisions

### D1. Модель — данные (`ENEMY_MODELS`), рисование — один построитель

Заменяем 19 веток одним общим построителем, который получает дескриптор:

```python
ENEMY_MODELS = {
  'soldier': EnemyModel(
      h=56, w=0.40, pal=..., parts=(
          Part('legs',  kind='legs',   w=0.42, h=0.42, y=0.00, detail=1),
          Part('torso', kind='torso', w=0.44, h=0.34, y=0.42, detail=2),
          Part('head',  kind='head',  r=0.11,          y=0.80, detail=3),
          Part('arm_l', kind='arm',  ...),
          Part('arm_r', kind='arm',  ...),   # в front — оружие
          Part('wpn',  kind='gun',   ...),
      ),
      anim={'idle': 2, 'walk': 6, 'attack': 3, 'death': 5},
      stance='biped',   # quadruped | floater | biped | blob | turret
  ),
  ...
}
```

`stance` задаёт, как части переиспользуются в 8 ракурсах: `biped`
(голова/торс/ноги/руки), `quadruped` (корпус + 4 ноги, длина по силуэту),
`floater` (парящее ядро + щупальца/шипы), `blob` (одна масса + глаза),
`turret` (тело-башня + орудийные стволы).

Альтернатива: расширить существующий `get_bot_surface` до «универсального
провайдера» через `gs.sprite_provider`. Отклонено: провайдер подписан на
сигнатуру бота (`color, w, h, frame, state, pa, wpn, view`) — это одна из
причин, почему enemy-арт и не пошёл в кэш. Менять контракт слота значит
ломать `smoke_content_providers.py` и границу движка шире, чем нужно для
этого change. Враг получает собственный слот (`gs.enemy_surface_provider`)
с собственной сигнатурой, включающей тип.

### D2. Где живёт построитель: новый модуль `client/enemy_models.py`

`engine/` не должен «ничего создавать с нуля», а `tools/check_engine_imports.py`
запрещает генерацию enemy-арта в движке. Поэтому:

- `client/enemy_models.py` — **всё** процедурное: `ENEMY_MODELS`,
  построитель поверхности по (дескриптор, ракурс, кадр, размер, детализация),
  кэш поверхностей. Чистый pygame, без знания о сети.
- `engine/game_state.py` — новый слот `enemy_surface_provider` (по умолчанию
  `None`) плюс флаг отката `enemy_models_enabled` (по умолчанию `True`).
- `client/bridge.py` регистрирует его (одна строка рядом с
  `gs.sprite_provider`), т.е. **до первого кадра**, и чистит кэш на смене
  карты.
- `engine/rendering.py` при `provider is None` или
  `enemy_models_enabled = False` рисует нейтральную заглушку (светлый
  силуэт-призрак по размеру врага) — деградация предсказуема, кадр не
  падает. Так же, как сейчас деградирует бот.

Слот — **диспетчер, а не одна функция**: врагу нужны не только тела, но и
корпуса, тень, оглушение, вспышка урона, оверлей рывка и глаза в темноте, и
у каждого своя сигнатура. Один слот с `kind` не даёт завести семь почти
одинаковых слотов в `game_state`, и оставляет смысл у вызова
(`provider('corpse', t, px, ...)`) — иначе по месту вызова не видно, что
запрашивается:

```python
ENEMY_SURFACES(kind, etype, px, frame=0, state='idle', view=0,
               detail=3, col=None, step=0, base=None) -> Surface | None
ENEMY_SURFACES.clear()
ENEMY_SURFACES.stats()
```

`kind` — закрытый набор (`model`, `corpse`, `shadow`, `stun`, `flash`,
`rush`, `eyes`); неизвестный тип врага (`custom:*`, мусор) даёт
человекообразный фолбэк, а не пустую поверхность.

### D2a. Куда именно вставляется кэшированная поверхность

В `gs.screen`, одной операцией `Surface.blit`, а не в `Frame` через
`blit_mini`. Причина — `SCALE = 4`: внутренний буфер 320×240 (или по
разрешению) масштабируется в окно вчетверо, так что вставка через фреймбуфер
съедала бы разрешение в 4 раза и рисовала бы модель в четверть экрана.
Противоположный аргумент («буфер дешевле, blit_mini — одна запись») отпал
вместе с требованием сохранить экранные координаты. `Frame.blit_mini`,
`engine.sprite_cache.mini` и свет-зайкание в луче остаются для ботов,
предметов и частиц — там, где низкое внутреннее разрешение не заметно.

Следствие: `engine/sprite_cache.mini()` в пути врага не вызывается. Кэш
моделей — отдельный, в клиенте (см. D4).

Альтернатива: построитель в `engine/rendering.py`. Отклонено прямо —
нарушает границу движка, которую `AGENTS.md` и `updating_engine` провели
намеренно, и `check_engine_imports.py` это поймает.

### D3. Ракурс: bearing → 8 секторов по 45°, гистерезис не нужен

```python
def view_index(bearing, cache: dict[int, int]) -> int:
    a = (bearing + math.pi / 8.0) % (2 * math.pi) - math.pi
    return int((a + math.pi) / (math.pi / 4)) % 8
```

Ключевой момент: `+ π/8` внутри даёт «округление к ближайшему», поэтому
модель меняется только при пересечении границы, а не на каждом кадре — это и
есть требование «стабильность на границе» без отдельного гистерезиса.
`view` в кэш-слоте передаётся как индекс 0..7.

Для типа с вытянутым силуэтом (`quadruped`: `dog`, `pinkie`, `lost_soul`,
`arachnotron`, `boss_spider`) ракурс меняет **длину**, а не только набор
деталей: в профильном ракурсе ширина силуэта максимальна, во фронтальном
минимальна (≈0.45 от максимума). Без этого «собака» выглядит как кошка.

Альтернатива: 16 ракурсов. Отклонено: ×2 к числу кэшируемых вариантов при
визуально почти нулевом выигрыше на внутреннем буфере 320×240, где босс в
профиль занимает ~60 px по ширине.

Альтернатива: 3D-поворот квада (как у `get_bot_surface`) — 8× стоимость
построения и перспективные искажения на billboard.

### D4. Неквадратные спрайты: два кэша, не один

Кэш моделей врагов и `engine/sprite_cache` решают разные задачи и не
дублируют друг друга.

**`engine/sprite_cache` (для ботов, предметов, частиц).** Сейчас `mini()`
возвращает `size × size`. Манкубус, боссы и `arachnotron` — широкие;
`cacodemon`, `healer` — округлые, поэтому квадратная навязка даёт либо
искажение пропорций, либо пустые прозрачные поля. Решение: `mini()` получает
`aspect: float = 1.0` и возвращает `(w, h, data)`, где `h = size`,
`w = clamp(round(size * aspect))`. `aspect` в ключ **не** добавляется — он
выводится из типа, а тип в ключе уже есть. `size_for_bucket` не меняется
(высота = бакет). `SpriteCache` дополнительно получает `clear()` (смена
карты, смена тира) и LRU на `collections.OrderedDict` с
`popitem(last=False)` — вместо O(n) `list.remove` на каждый спрайт.
Рендерер зовёт `set_view(gs.view_dist)` (через `set_view_dist`), поэтому
`_edges` наконец перестаёт навсегда быть `bucket_edges(900.0)`.

**Кэш моделей врагов (в клиенте, `client/enemy_models.py`).** Отдельный
по необходимости, а не по вкусу: модель — это `Surface` (нужен альфа-блендинг
на экране, см. D2a), а `mini()` отдаёт распакованный RGBA-блоб, который
вставляется во фреймбуфер. Строки кэша там тоже другие: без бакетов света
(свет применяется к модели, а не запекается в неё) и без бакетов дальности —
вместо них лестница размеров. Ключ: (kind, тип, размер по лестнице, ракурс,
состояние, кадр, детализация, цвет/шаг оверлея).

Бюджеты: `CACHE_MAX_ENTRIES = 4096` записей и `CACHE_MAX_PIXELS = 12 000 000`
пикселей (≈48 МиБ RGBA) для моделей, отдельно от байтового бюджета
`DEFAULT_SPRITE_CACHE` — это и есть ответ на первый Open Question: общий
бюджет смешивал бы несопоставимые единицы (байты мини-спрайтов и пиксели
моделей) и не дал бы предсказуемой памяти.

Лестница размеров — обязательна, а не оптимизация: непрерывный диапазон
высот на 320×240 дал бы отдельную поверхность на каждый пиксель при ходьбе.
`SIZE_STEPS` (6…256, 20 ступеней) схлопывает 252 возможных высоты в 19
записей, что и проверяет `smoke_enemy_models.py`.

### D5. Оверлеи состояния — предрассчитанные спрайты, а не заливки

Четыре эффекта перестают создавать поверхности. Каждый — маленький
предрассчитанный RGBA-спрайт в кэше слота `enemy_surface_provider`
(ключ включает `effect` и `step`):

| Эффект | Сейчас | Стало |
|---|---|---|
| тень | эллипс `Surface(w*2, w//2)` на врага на кадр | спрайт тени по (тип, бакет); масштабируется по `sh` выборкой, без новых аллокаций |
| оглушение | `fill((20,20,60,alpha))` прямоугольник + sin по тику | полупрозрачный кэшированный спрайт-«шум», 4 шага по alpha |
| вспышка урона | красный прямоугольник `0.4sh × 0.6sh` | кэшированный красный RGBA по силуэту типа, 6 шагов затухания |
| свечение rush | эллипс `Surface` | кэшированный контурный оверлей по силуэту типа, 4 шага пульса |
| глаза в темноте | 2 × `Surface(8,8)` на врага на кадр | те же глаза, но позиция/размер из кэшированной модели; при `glow_alpha <= 20` ничего не рисуется |

Интенсивность берётся из `d_flash` / `stun` (кадровые счётчики), а не из
`tick` — это убирает зависимость эффекта от FPS и делает затухание
детерминированным (требование спеки «затухать по кадрам»).

Оверлеи по силуэту строятся через `pygame.mask`, и там есть две ловушки
pygame 2.6, обе пойманные `smoke_enemy_models.py`: `Mask.outline()` отдаёт
**плоский кортеж точек** (а на части сборок — список кортежей), поэтому его
нельзя блютить напрямую — сначала растеризуем кольцо через `draw.lines`;
а заливка ауры аддитивом по всему прямоугольнику без кольца превращается в
красный прямоугольник — аура умножается на кольцо, и светится только контур.

Альтернатива: один общий «тир-овал» для всех оверлеев, привязанный к
размеру, а не к силуэту. Отклонено: заливка по прямоугольнику — текущий
дефект; оверлей по силуэту стоит того же кэша и выглядит существенно лучше.

### D6. Визуальный масштаб — из `ENEMY_GAME_HEIGHTS` и `w` в дескрипторе

`ENEMY_GAME_HEIGHTS` остаётся источником игровой высоты (её использует
`sector_render.project_object`). Дескриптор модели добавляет `w` (ширина
силуэта в долях высоты) и `anchor` (0 — стоит на полу, >0 — парит, как
`cacodemon` 0.30 и `pain_elemental` 0.18). Присваивание `ground_y` из
секторного пола и вертикальные смещения сохраняются — механика
позиционирования не меняется, меняется только картинка внутри.

`w` подобран по классам: `mancubus` 1.00, `boss_spider` 1.55,
`boss_cyber` 0.78, `cacodemon` 0.62, `soldier` 0.40, `lost_soul` 0.34.
`dog` 0.80 и `pinkie` 0.78 — не «жирные», а длинные: это профильный
силуэт четвероногого, и во фронтальном ракурсе нарисованная ширина падает
примерно вдвое (0.55–0.77 от профильной), тогда как поверхность остаётся
одного размера. Именно поэтому `w` **не** обязан быть пропорционален
`ENEMY_GAME_HEIGHTS` и сравнивать классы между собой нельзя: «жирный
двуного» против «длинного четвероногого» — разные оси.

Инвариант, который проверяется тестом, — **порядок внутри класса**:
`imp < boss_cyber`, `lost_soul < artillery`, `archvile < boss_baron`,
`dog < boss_spider`, `pinkie < arachnotron`, и `mancubus` шире любого
двуногого. Плюс «узнаваемость в каждом ракурсе»: нарисованная ширина
не проседает ниже 45% максимальной по восьми ракурсам, а `dog`/`pinkie`/
`arachnotron`/`boss_spider` во фронтальном ракурсе уже 85% профильной
(у `mancubus` наоборот — он шире впереди, у него две руки).

Прошлый вариант инварианта («`w` пропорционален `ENEMY_GAME_HEIGHTS` в
пределах ±25%») был неверным: он запрещал саму идею различия силуэтов и
требовал, чтобы `dog` был «уже» `boss_spider`, хотя у первого профиль
длиннее при меньшей высоте. Заменён на внутриклассовый порядок выше.

Альтернатива: поправить `ENEMY_RADIUS` по типам. Отклонено: это меняет
серверную геометрию и попадания — за пределами «визуал + баланс
поведения» в согласованном смысле (поведение = читаемость классов, не
хитбоксы).

### D7. Состояния анимации выводятся на клиенте, протокол не меняется

В снимке мира у врага есть только `id`, `x`, `y`, `angle`, `type`, `hp`,
`state` — ни `stun`, ни `ls`, ни `d_flash` по проводу не приходят. Поэтому
`client/bridge.py` держит предыдущий снимок по `id` и выводит недостающее
из дельт, а `anim_state_of` уже читает готовые счётчики:

```python
# client/bridge.py, локально из дельт снимка
moving  = dist(cur, prev) > 0.35                  # px за кадр
d_flash = 5 if cur['hp'] < prev['hp'] else max(0, d_flash - 1)
attack  = dist(cur, prev) > 2.2 and now - last_attack < ATK_MS

# client/enemy_models.py
def anim_state_of(e, now):
    if e.get('dying', 0) > 0:                      return 'death'
    if e.get('stun', 0) > 0:                       return 'pain'
    if e.get('ls', 0) and now - e['ls'] < ATK_MS:  return 'attack'
    if e.get('moving'):                            return 'walk'
    return 'idle'
```

Порядок приоритетов — «смерть > оглушение > атака > ходьба > покой», чтобы
смерть и оглушение не терялись за анимацией ходьбы. Кадр анимации —
производная от состояния и **локального** времени (`advance_clock`), а не
идентификатор кадра из снимка; смена состояния перезапускает цикл с нуля.

Это ровно тот случай, где «данных в кадре» не хватает и добрать их можно
только клиентской дельтой: сеть остаётся без изменений (D7 исходной формулировки
«из снимка мира» сохранена — `pa` и координаты из снимка и есть единственный
источник ракурса), а при `smoke_integration_combat` поведение бота не
меняется ни на бит.

### D8. Приоритет: порядок отрисовки и баги, найденные попутно

Обход `objs` (`:1692-1693`) уже сортирует всё по убыванию расстояния, и
враги в нём участвуют, так что внутрьрослевое пересечение враг↔враг уже
корректно. Вне этого change остаются (фиксируются как известные долги в
tasks, не в скоуп):

- боты и другие игроки рисуются в отдельных циклах **после** всех
  мировых спрайтов (`:1892`, `:1948`) — враг за ботом всегда перекрыт;
- `continue` в цикле `objs` при провале проекции маркера выхода
  (`:1873`, и аналоги `:1906`, `:1963`) пропускает остаток итерации
  текущего спрайта.

Обе правки — отдельный change с собственным регрессионным тестом; в этом
change они только не ухудшаются.

## Risks / Trade-offs

- **Карьер кэша.** 20 типов × 8 ракурсов × ~4 состояния × N кадров
  анимации × бакеты × 16 уровней света — потенциально сотни тысяч записей.
  → Ключ кэша по (тип, ракурс, кадр, детализация, свет, бакет), бюджет
  8 МиБ с LRU (D4), плюс **сжатие числа состояний**: `pain` и `idle`
  различаются только оверлеем, а не отдельной геометрией — одна модель,
  разные оверлеи. В smoke-тесте — проверка, что после прогона всех 20×8×5
  комбинаций `stats()["bytes"] <= max_bytes` и `items` в разумных пределах.

- **Стоимость первого кадра.** Холодный кэш = десятки построений
  поверхностей за кадр. → Прогрев при загрузке карты: `bridge` (или
  первый кадр) заранее строит модель каждого типа в радиусе N бакетов и в
  текущем уровне света. На тире «Быстрая» — только фронтальный и
  профильный ракурсы, без анимации ходьбы.

- **Регресс производительности при неверном ключе.** Если в ключ не
  попадёт `detail` или `view`, тир «Быстрая» покажет арт «Хорошей» или
  ракурс «поплывёт». → Тест: модель, построенная для (view=0, detail=2),
  пиксельно отличается от (view=4, detail=2) и от (view=0, detail=0).

- **Расхождение с `smoke_sprites.py`.** Он сравнивает вывод `mini()` с
  ручным эталоном по квадрату. → Эталон обновляется на неквадратный
  (проверка `w * h * 4 == len(data)` и пропорции), старые проверки
  попадания/промаха/LRU сохраняются.

- **Размер `engine/rendering.py`.** Удаление ~790 строк и 19 веток — большой
  дифф. → Рисование моделей уезжает в `client/enemy_models.py`;
  в `rendering.py` остаётся тонкий слой (выбор кэша, позиция, оверлеи,
  HP-бар). Дифф разбивается на коммиты по смыслу: реестр → ракурс →
  кэш → оверлеи → corpses.

- **Арт на доске 320×240.** Часть деталей (бляхи, когти, чешуя) на
  расстоянии не читается и только жрёт кэш. → Детализация описана
  уровнями, и уровни 2–3 деталей включаются только для ближних бакетов;
  `detail_ratio` тира решает, какой уровень вообще доступен.

- **Визуал может стать «лучше, но нечестнее».** Увеличение ширины
  силуэта при неизменном hitbox делает врага легче целиться мышкой, чем
  было. → `w` ограничен сверху так, чтобы силуэт не превышал
  `ENEMY_RADIUS`-проекцию с большим запасом; конкретные значения
  фиксируются в дизайне дескрипторов и проверяются визуально на
  acceptance-скриншотах тиров.

## Migration Plan

1. Завести `client/enemy_models.py` + `ENEMY_MODELS` + слот
   `gs.enemy_surface_provider` + `ENEMY_SURFACES` + регистрация в `bridge`.
   Движок продолжает рисовать по-старому — новое подключено, но не
   используется (feature flag не нужен, достаточно не вызывать).
2. Ракурс + кэш: `SpriteCache` (`aspect`, `clear`, LRU на `OrderedDict`),
   вызов `set_view_dist(gs.view_dist)`; кэш моделей в
   `client/enemy_models.py` с лестницей размеров.
3. Переключить `draw_enemy_sprite` на провайдер с фолбэком, удалить 19
   веток.
4. Оверлеи на кэшированные спрайты, убрать пять `Surface` из пути.
5. `draw_corpse` на дескриптор + общий фолбэк.
6. Тир: `enemy_detail()` в `engine/quality.py` (вместо мёртвого
   `sprite_ratio`), матрица `MIN/MAX_ENEMY_DETAIL`.
7. Удалить `engine/sprites.py`, мёртвый enemy-арт из
   `client/sprite_factory.py`, `engine/rendering.py:_ENEMY_SPRITE_MAP` и
   осиротевший дубль `engine/map_editor.py`; расширить
   `tools/check_engine_imports.py` запретом enemy-арта в движке.
8. Откат: всё в шагах 1–4 — за флагом `gs.enemy_models_enabled`
   (в `game_state.py`, по умолчанию `True`, откат — `False` без правки
   кода рендерера). Шаги 5–7 — чистка, откат = revert.
