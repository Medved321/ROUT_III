## Context

См. proposal.md — Why. Апдейтер состоит из хендшейка (`HELLO`/`HELLO_ACK`,
`server/server.py:104-137`, `client/network_client.py:87-124`), диалога
(`client/client.py:167-236`) и раздачи файла (`server/server.py:139-152`).
Версия клиента берётся из `shared/version.py`; последний релиз — из
`releases/latest.txt` (`shared/releases.py:57-64`). Сборка
(`tools/build_client.py:66-88`) пишет версию только в staging-копию.

Сейчас решение об обновлении — это `!=`, а не «новее», память о пропуске
отсутствует, а исходники не синхронизируются со сборкой.

## Goals / Non-Goals

**Goals:**
- Устранить бесконечный диалог при запуске из исходников и при отказе.
- Единый компаратор версий для сервера, апдейтера и лаунчера.
- Сохранить обновление действительно устаревших клиентов.

**Non-Goals:**
- Не менять формат `HELLO_ACK`, канал раздачи файла, sha256-проверку.
- Не вводить каналы/подписки обновлений и фоновую проверку.
- Не менять раскладку `releases/`.

## Decisions

### D1: Строго-новее вместо неравенства
`has_update = accepted and release is not None and is_newer(release["version"],
client_version)`. Равная версия — обновление не нужно; более новая версия
клиента — откат не предлагаем. Это снимает предложение «обновиться до самого
себя» и защищает от понижения версии.

_Альтернатива:_ сравнивать строки лексикографически — неверно для `1.0.10`
vs `1.0.9`; отклонена.

### D2: Синхронизация исходной версии при сборке
`tools/build_client.py --set-latest` дополнительно перезаписывает
`CLIENT_VERSION` в исходном `shared/version.py` (сохраняя `PROTOCOL_VERSION`).
Тогда после публикации `1.0.2` исходники тоже сообщают `1.0.2`, и запуск из
IDE/`run_client.py` не получает предложение.

_Альтернатива:_ клиент из исходников рапортует «эффективную» версию =
максимум из `CLIENT_VERSION` и `releases/latest.txt`. Отклонена: код на
диске не соответствует сообщаемой версии, что маскирует реальное расхождение.

### D3: Память об отклонённой версии
При отказе (`N`/`Esc` в `client/client.py:205-236`) клиент сохраняет
`offer.version` в `config.json` (`client/settings.py`). На следующем
подключении диалог для этой же версии не показывается. Версия строго новее
сохранённой снова показывает диалог. Ручной сброс — очистка ключа в
`config.json`; переменная `ROUT_UPDATE_ANSWER` сохраняет приоритет.

_Альтернатива:_ отдельная кнопка «не напоминать» — лишний UI; отклонение и
есть решение «не сейчас, для этой версии».

### D4: Единый компаратор
`shared/releases.py` получает `parse_version(str) -> tuple[int, ...]` и
`is_newer(candidate, base) -> bool` (нечисловые/битые версии — не новее).
`tools/launch_client.py` (`_components`/`newer`) переводится на них, чтобы
правило версий было одно.

## Risks / Trade-offs

- **[Сборка меняет исходную версию]** Разработка поверх релиза будет
  маркироваться версией релиза. → Приемлемо: так исходники и артефакт
  совпадают; при необходимости версия поднимается вручную перед сборкой.
- **[Пропуск подавляет напоминание]** Игрок, отказавшийся один раз, не
  увидит эту же версию снова. → Строго более новые версии показываются;
  пропуск сбрасывается вручную.
- **[Совместимость]** Wire-формат и логика скачивания не меняются, старые
  клиенты продолжают получать предложения для строго новых версий.
