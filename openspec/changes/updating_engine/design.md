## Context

Аудит состава `engine/` (15 модулей) показывает, что рендером не являются
два модуля:

- `engine/sprites.py` (228 строк) — процедурное создание спрайтов:
  `get_bot_surface` (поверхность бота по цвету/кадру/взгляду/оружию),
  `get_enemy_surface` + `_draw_enemy_on_surf` (отрисовка типов врагов),
  `render_sprite_frame`, `ANIM_STATES`/`init_anim`/`update_anim`/
  `set_anim_state`/`get_anim_frame`, кеш кадров `FRAME_CACHE`. Используется
  движком ровно в одном месте: `engine/rendering.py:1835` — `get_bot_surface`
  для ботов (deathmatch). Остальное — мёртвый код: `get_enemy_surface`,
  `render_sprite_frame` и хелперы анимации внутри движка не вызываются.
- `engine/map_editor.py` (136 строк) — модель тайлового редактора: `TileEditor`
  (буфер, `resize`, `set_cell`, `to_game_map`/`from_game_map`, undo-снимки),
  палитра `TB_ITEMS`/`MAT_COLORS`, таблицы `CHAR_TO_TILE`/`TILE_TO_CHAR`/
  `grid_to_tiles`/`tiles_to_grid`, списки `ENEMY_NAMES`/`ITEM_NAMES`,
  отображение `TILE_CHAR_TO_TEX`. Потребители: `client/editor_screen.py`
  (`TileEditor`, `TB_ITEMS`, `MAT_COLORS`, `CHAR_TO_TILE`),
  `client/sector_editor_screen.py` (`ENEMY_NAMES`, `ITEM_NAMES`),
  `smoke_text_map.py`. В движке из всего этого используется ровно одна
  вещь — `TILE_CHAR_TO_TEX` в `engine/rendering.py:10` (два обращения на
  строки 1532 и 1536).

Следствия текущего состояния:

- `engine/map_editor.py` — единственная причина, по которой движок импортирует
  `shared.map_data` (ради `GameMap` в `TileEditor.to_game_map`). Убрав её,
  движок перестаёт использовать все три разрешённых контрактных модуля
  (`shared.sector_map`, `shared.mt1`, `shared.map_data`).
- В движке нет ни одного обращения к сетевым/клиентским модулям, но есть
  импорт клиентского по смыслу модуля: рендер «знает», что такое символ
  тайла и какому врагу какая картинка.
- `client/bridge.py:26` дублирует таблицу `CHAR_TO_TILE` в обратную сторону
  (`_TILE_TO_CHAR`) и ссылается на `map_editor.TILE_CHAR_TO_TEX` в комментарии.
- `shared/text_map.py` (stdlib-only, зеркалирует типы текстур и сущностей)
  в докстринге указывает `engine/map_editor.py` как источник истины.
- `engine/sprite_cache.py` принимает спрайт как `build`-callable и ничего не
  импортирует из `sprites.py` — переезд его не затрагивает; страдают только
  вызывающие.

Тайловый путь рендера работает с символьной сеткой `gs.MAP`: `bridge`
преобразует целочисленные тайлы `GameMap` в символы, а движок по символу
выбирает текстуру (`TILE_CHAR_TO_TEX`). Значит контракт, который движку
действительно нужен, — это отображение «символ тайла → имя текстуры» и
«параметры бота → `pygame.Surface`».

## Goals / Non-Goals

**Goals:**
- `engine/` содержит только рендер: ни генерации спрайтов, ни модели
  редактора, ни палитр.
- Движок не импортирует `shared.map_data` — все три оставшихся разрешённых
  контракта (`shared.sector_map`, `shared.mt1`) используются, лишние убраны.
- Единственная точка связывания — слоты в `engine.game_state`; их наполняет
  клиент через `bridge`.
- Ни одного изменения наблюдаемого поведения: пиксели кадра, формат карт
  (`.json`/`.mt1`/`.mts`), протокол, 60 FPS.

**Non-Goals:**
- Не удалять мёртвый дубликат `client/engine/` (10 модулей) — отдельная
  задача; в этом change он не трогается и не должен сломать сборку.
- Не переносить в клиент `engine/textures.py` (процедурные текстуры) и
  `engine/sprite_cache.py` (кеш) — это часть рендера.
- Не вводить файловый формат спрайтов/ассетов: по-прежнему рисуем
  примитивами pygame, только в клиенте.
- Не переписывать `TileEditor` и палитру — только место жительства.

## Decisions

### D1. Куда переезжает

```
ROUT III/
├── engine/            # 13 модулей: рендер-ядро
├── client/
│   ├── sprite_factory.py   # ← engine/sprites.py
│   ├── map_editor.py       # ← engine/map_editor.py
│   ├── editor_screen.py    # экран тайлового редактора
│   └── sector_editor_screen.py
└── shared/            # карты/протокол
```

Рядом с единственными потребителями (`bridge.py`, экраны редакторов) и
вне `engine/`. Альтернатива — `client/assets/`: отклонена, потому что
призрачно раздувает пакет из двух файлов и создаёт вложенность импортов
`client.assets.map_editor` ради плоского `client.map_editor`.

### D2. Провайдеры в `engine.game_state`

```python
# engine/game_state.py
sprite_provider = None   # callable(color, w, h, frame, state, pa, wpn, view) -> Surface
tile_provider   = None   # callable(tile_char) -> str (имя текстуры), None -> 'wall'
```

Вызов в рендере — ровно одна строка на место:

```python
_surface_of_bot = gs.sprite_provider
surf = _surface_of_bot(pcol, sh2, sh2, frame, state, bot.get('pa', 0),
                       bot.get('wpn', 1), view=bot_view) if _surface_of_bot else _BLANK
an = gs.tile_provider(at) if gs.tile_provider else 'wall'
```

Свойства:

- **Ноль импортов.** Движок не знает, откуда пришла поверхность, — это
  ровно то свойство, ради которого переезд и делается.
- **Деградация вместо падения.** `None` → для ботов пустая прозрачная
  поверхность, для тайлов `'wall'`. Офлайн-скрипты (`smoke_engine_standalone.py`)
  и любой сторонний потребитель движка остаются рабочими без единой строки
  регистрации.
- **Никаких ABC/протоколов.** `game_state` — намеренно «словарь всего»;
  вводить туда интерфейсный слой ради двух callable — оверинжиниринг.
  Контракт (сигнатура) фиксируется спекой и smoke-тестом.

Альтернативы, отклонённые:

- **Таблицу тайлов оставить в движке как «рендер-константу».** Кроме
  одного обращения в движке её используют только редакторы, и она по
  определению описывает палитру редактора — то есть проблема не решается,
  а просто переименовывается.
- **Положить `TILE_CHAR_TO_TEX` в `shared/`** (рядом с зеркалом в
  `text_map.py`). Отклонено: это таблица палитры редактора, а не формат
  карты; `shared/` — контракт с сервером, и новый модуль в нём создал бы
  третью копию тех же данных рядом с `text_map`.
- **Реестр на инстансах** (`rendering.register_sprites(fn)`). Хуже, чем
  слот в `gs`: рендер уже читает всё из `gs`, лишний уровень состояния.

### D3. Что делает `client/sprite_factory.py`

Переносится файл целиком, без переписывания логики (важно: графика
должна остаться пиксель в пиксель). Меняются только вещи, связанные с
пакетом:

- `from engine.constants import TILE` — импорт не нужен (в модуле `TILE`
  не используется) → удалить; после этого модуль не зависит от движка
  вообще.
- Мёртвый код (`get_enemy_surface`, `_draw_enemy_on_surf`,
  `render_sprite_frame`, хелперы анимации) — **оставить** и перенести
  вместе с остальным: он не мешает границе импортов, а удаление меняет
  публичный API модуля. Отдельным change, если понадобится.

Тонкость с кешем: `FRAME_CACHE` — глобальный словарь поверхностей внутри
модуля. Он остаётся в `client/sprite_factory.py`, то есть кеш спрайтов
живёт в клиенте, а движок его не видит. Это и есть цель: создание и
кэширование спрайтов — не забота рендера.

### D4. Что делает `client/map_editor.py`

Перенос файла целиком. `from shared.map_data import GameMap` остаётся
(нужен `TileEditor.to_game_map`) — это разрешённый контракт и для клиента.
`CHAR_TO_TILE`/`TILE_TO_CHAR` — единственный источник истины для формата,
поэтому дубликат `_TILE_TO_CHAR` в `bridge.py:26` заменяется импортом
`CHAR_TO_TILE` (таблица инвертируется один раз на импорте). Комментарий
`bridge.py:25` и докстринг `shared/text_map.py:36-38, 77` обновляются на
новое место жительства.

### D5. Импортёры и регрессия

- `client/editor_screen.py:13`, `client/sector_editor_screen.py:19`:
  `engine.map_editor` → `client.map_editor`.
- `smoke_text_map.py:488`: то же.
- `engine/rendering.py`: убрать `from engine.map_editor import
  TILE_CHAR_TO_TEX`, читать `gs.tile_provider`; убрать
  `from engine.sprites import get_bot_surface`, читать `gs.sprite_provider`.
- `client/bridge.py`: зарегистрировать провайдеры (см. D6) — до первого
  кадра, на уровне модуля (вызов при импорте) либо в функции
  инициализации состояния, если она есть; выбор — по месту, где bridge
  уже наполняет `gs` (иначе порядок регистрации станет неявным).
- Smoke, рендерящие тайловый режим с проверкой текстур
  (`smoke_framebuffer_tile.py` — проверяет различие текстур север/юг),
  обязаны зарегистрировать `TILE_CHAR_TO_TEX` как `gs.tile_provider`,
  иначе проверка потеряет смысл (все стены станут `'wall'`).
- `smoke_sprites.py` не затрагивается: `sprite_cache` остаётся в движке.
- `tools/build_client.py` уже включает и `client/`, и `engine/` — правок
  нет.

### D6. Где регистрируются провайдеры

В `client/bridge.py`, рядом с прочим наполнением `gs` (уже делается при
переходе в партию/инициализации движка), и дополнительно в
`smoke_engine_standalone.py`-подобных офлайн-сценариях — по необходимости.
Регистрация идемпотентна (присваивание callable), поэтому порядок вызовов
некритичен, но первый кадр SHALL идти после регистрации — это закреплено
сценарием спеки.

### D7. Сканер границ

`tools/check_engine_imports.py` дополняется:

- `shared.map_data` переносится из `ALLOWED_SHARED` в запрещённые;
  `ALLOWED_SHARED` = `{shared.sector_map, shared.mt1}`;
- добавляется проверка состава: `FORBIDDEN_MODULES = {"sprites.py",
  "map_editor.py"}` — падение, если такой файл снова появится в `engine/`.

Так граница «движок не создаёт содержимого» становится проверяемой
автоматически, а не договорённостью.

## Risks / Trade-offs

- **Сломается рендер бота в deathmatch, если провайдер не зарегистрирован**
  (боты исчезнут вместо отрисовки) → smoke на связку «bridge зарегистрировал
  провайдер → `rendering` получил поверхность», плюс деградация вместо
  исключения (D2) и регистрация до первого кадра (D6).
- **Тихое исчезновение разнообразия текстур в тестах**: забытый
  `tile_provider` в smoke даёт «зелёный» тест с однородными стенами →
  в smoke с проверкой текстур регистрация обязательна (D5), а новый
  smoke явно проверяет, что разные тайлы дают разные текстуры.
- **Возврат зависимости через новый импорт**: любой новый `from engine…`
  в перенесённых модулях или `shared.map_data` в движке → сканер
  `check_engine_imports.py` (D7) ломает сборку в тот же момент.
- **Дублирование `CHAR_TO_TILE`** в `bridge.py` → заменяется импортом (D4),
  иначе таблицы снова разъедутся.
- **Пиксельная регрессия графики** при переносе `sprites.py` → перенос
  файла без правки логики (D3) + сравнение кадра до/после в smoke.
- **Трёхуровневая вложенность `client.map_editor`** vs «плоский» клиент →
  приемлемо: имя файла совпадает с прежним, меняется только пакет, так что
  диффы и сообщения об ошибках остаются читаемыми.
- **Офлайн-потребители движка** (тесты, сторонние рендеры) получают
  нейтральные стены вместо текстур → это осознанная цена независимости;
  регистрация провайдера — одна строка.

## Migration Plan

1. `engine/sprites.py` → `client/sprite_factory.py`, `engine/map_editor.py`
   → `client/map_editor.py` (копия, правка только импортов внутри).
2. Слоты `sprite_provider`/`tile_provider` в `engine/game_state.py` +
   fallback в `engine/rendering.py` (два места вызова).
3. `client/bridge.py`: регистрация провайдеров, `_TILE_TO_CHAR` →
   `CHAR_TO_TILE` из нового модуля.
4. Переключение импортёров (`editor_screen.py`, `sector_editor_screen.py`,
   `smoke_text_map.py`) и регистрация `tile_provider` в тайловых smoke.
5. Удаление `engine/sprites.py` и `engine/map_editor.py`.
6. `tools/check_engine_imports.py`: запрет `shared.map_data` + проверка
   состава.
7. Регрессия: все smoke (`py -3.12 smoke_*.py`), запуск клиента
   (лобби → редактор → F5 играть на карте → deathmatch с ботами),
   `tools/check_engine_imports.py`, `openspec validate --strict`.
8. Обновление докстрингов (`shared/text_map.py`) и `AGENTS.md` (раздел
   «Граница движка»).

Откат: всё — перестановка файлов и две строки чтения из `gs`; откат =
вернуть файлы в `engine/` и вернуть прямые импорты, без миграции данных
(форматы карт не менялись).
