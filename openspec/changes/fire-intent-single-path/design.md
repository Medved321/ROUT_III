## Context

Текущее состояние (детали — в `proposal.md`):

- Клиент открывает собственные врата темпа в `_process_input`
  (`client/client.py:773-787`) и **до** отправки чего-либо проигрывает отдачу
  (`_fire_anim_until`, строка 782).
- `shoot_pressed` живёт ровно один кадр: `InputHandler.update()` обнуляет его в
  строке 104 на каждом кадре.
- `send_fire()` вызывается **внутри** условия врат и **только** при
  `shoot_pressed` (строка 786). Удержание кнопки в `FIRE` не попадает никогда.
- `_input_snapshot()` (строка 623) кладёт `input_handler.shoot` в каждый пакет
  управления, и сервер из этого поля создаёт выстрел
  (`server/server.py:319`), а `_apply_input` выставляет `pl.state = 2` по
  нажатой кнопке (строка 326), независимо от результата.

Прецедент в проекте уже есть: `dash_pressed` — такой же одно-кадровый фронт —
не отбрасывается, а защёлкивается в `_dash_pending` внутри `_input_snapshot`
(строка 614), с явным комментарием «a single-frame edge is never lost between
two 25 Hz sends». Для огня этот приём не применён.

Ограничения: формат `PLAYER_INPUT` и `FIRE` менять нельзя (см. `SPEC.md`),
новых пакетов не вводим, сервер остаётся stdlib-only, рендер не читает раскладку
клавиш. `PROTOCOL_VERSION` **поднимается** (см. D6), потому что решение едет в
существующем `WORLD_STATE`, а это рост записи игрока.

## Goals / Non-Goals

**Goals:**
- Один фронт нажатия = ровно один выстрел, независимо от того, попал кадр
  нажатия в открытые врата темпа или нет.
- Автоматический огонь удержанием и одиночный клик — один и тот же код.
- Отказ сервера виден, а не молчалив.
- Удержание кнопки не может создать выстрел, который игрок не «нажал», и не
  может удвоить выстрел.

**Non-Goals:**
- Точность попадания, баланс темпа огня, урон, прожектайлы — без изменений
  (они покрыты существующими требованиями `weapons-projectiles`).
- Ручной огонь (precision mode по аналогии с CS), переключатели оружия.
- Новая сетевая согласованность поверх существующей надёжной: восстановление
  `FIRE` уже гарантирует доставку.

## Decisions

### D1. Фронт нажатия защёлкивается, как у дэша

`send_fire()` перестаёт быть вложенным в условие врат темпа. Фронт
`shoot_pressed` защёлкивается (по образцу `_dash_pending`) и потребляется
**ровно один раз** при ближайшем открытии врат.

- Почему: сейчас клик, попавший в закрытые врата, теряется безвозвратно —
  это и есть «выстрел через раз». Пока фронт жив, удержание не отличить от
  нового клика, а защёлкивание даёт «одно нажатие = один интент».
- Альтернатива: поднять частоту кадров/врат, чтобы фронт попадал в окно —
  отвергнута, это маскировка и лишняя работа.
- Альтернатива: очередь интентов на клиенте с повтором — отвергнута, сложнее
  без выигрыша: защёлкивания одного фронта достаточно.

### D2. `PLAYER_INPUT.shoot` — только удержание, сервер из него не стреляет

Удаляем создание выстрела из `_apply_input` (вместе с `pl.state = 2` по
нажатой кнопке). Единственный путь — `FIRE` с `fire_seq`.

- Почему: два входа означают, что порядок доставки (25 Гц ненадёжный канал
  против надёжного `FIRE`) определяет, чей выстрел победит, а проигравший
  отбрасывается кулдауном без следа. Именно это даёт «отдача без пули».
- Альтернатива: оставить ввод как авто-огонь, а `FIRE` убрать — отвергнута:
  ввод ненадёжный, интент потеряется, и это ломает уже проверенный надёжный
  канал (`smoke_reliability.py`).

### D3. Удержание порождает интент на каждом открытии врат

Пока кнопка нажата, каждое открытие врат отправляет очередной `fire_seq`
(монотонный счётчик в `NetworkClient` уже есть, `_fire_seq`). Клик —
разовый интент; удержание — серия интентов; разница только в источнике
фронта.

- Почему: иначе удержание перестаёт стрелять после удаления пути из ввода.

### D4. Сервер возвращает решение, клиент сверяет по нему отдачу

`handle_shoot` перестаёт быть `None`-молчащим: он возвращает результат
(выстрел / отказ с причиной). Решение публикуется владельцу интента: в записи
игрока в `WORLD_STATE` едут последний принятый `fire_seq`, число тиков до
следующего разрешённого выстрела и код причины (см. D7).

- Клиент: предсказание остаётся (отдача стартует на интент — иначе ощущение
  оружия провалится), но авторитет у сервера: подтверждённый выстрел задаёт
  длительность (серверные тики — пол, предсказание не укорачивает), отклонённый
  — обрывает отдачу.
- Почему серверное время: ровно ту же задачу для дэша уже решил `state = 3`
  (`INPUT_FLAG_DASH` → состояние в снимке), и AGENTS.md требует, чтобы рендер
  читал подтверждённое сервером состояние, а не раскладку клавиш.
- Альтернатива: квитирование отдельным пакетом — отвергнута, `WORLD_STATE`
  идёт 20 Гц и уже несёт решение (а новый тип пакета означал бы ещё и новый
  обработчик с обеих сторон).
- Альтернатива: сдвинуть клиентские врата так, чтобы сервер всегда успевал —
  отвергнута, это подгонка симптома: рассинхрон часов и задержка сети остались бы.

### D5. Идемпотентность остаётся на `fire_seq`

Дубликат/переупорядоченный `fire_seq` → ноль созданий, ноль расхода патрона.
Возвращаемое решение это допускает (дубликат получает результат уже
выполненного выстрела), поэтому клиент не показывает вторую отдачу. `last_fire_seq`
двигается **только при принятом** интенте: иначе повторная доставка отклонённого
интента снова заняла бы слот «последнего принятого» и клиент потерял бы счётчик.

### D6. `PROTOCOL_VERSION` поднимается, а не молча меняется формат

Решение едет в существующем `WORLD_STATE`, поэтому запись игрока растёт с 21 до
27 байт (`fire_seq` uint32 + `fire_ready` uint8 + `fire_reason` uint8). Старый
клиент после 21 байта читает длину имени из мусора и разбирает снимок неверно —
тихо, без ошибки. Значит версия обязана вырасти (7 → 8), чтобы рукопожатие
отказало старому клиенту и автообновление доставило новую сборку. Формат
`PLAYER_INPUT` и `FIRE` при этом не меняется.

- Альтернатива: оставить версию 7 — отвергнута, это превращает несовместимость
  в тихую порчу данных вместо явного отказа.
- Альтернатива: отдельный пакет `FIRE_ACK` — отвергнута, `WORLD_STATE` идёт
  20 Гц и уже несёт решение, а новый тип пакета стоит отдельной обработки на обеих
  сторонах ради тех же 5 байт.

### D7. Причина отказа едет рядом со счётчиком

Отказ не двигает `fire_seq`, поэтому по одному счётчику клиент не может отличить
«сервер отказал» от «подтверждение ещё в пути». Обрывать отдачу в обоих случаях
нельзя (обрезается настоящий выстрел, чей ack задержался на снимок), не обрывать
тоже (пустой магазин под удержанием мигает вечно). Поэтому решение несёт
`fire_reason`, а клиент держит счётчик `_fire_undecided` = отправлено минус
подтверждено: обрыв делается ровно один раз на каждый реально отклонённый интент.

- Альтернатива: обрывать по «`fire_seq` не изменился, а снимок уже пришёл» —
  отвергнута, это отрезает отдачу настоящего выстрела при задержке ack на один
  снимок, то есть при обычной потере пакета.
- Альтернатива: ждать N снимков перед выводом об отказе — отвергнута, вводит
  искусственную задержку и всё равно ошибается на границе.

### D8. Байтовой дельты нет, и придумывать её незачем

Запись игрока — фиксированный struct, `WORLD_STATE` — полный снимок, поэтому
«кодировать решение дельтой, только при смене значения» на проводе невыполнимо:
5 байт пишутся в каждом снимке при любом раскладе. Реальная цель задачи — чтобы
удержание кнопки с пустым магазином не выглядело для игрока как непрерывная
стрельба. Эта цель достигается на уровне состояния: отказ не двигает
`fire_seq` (D5) и не удлиняет отдачу, а `fire_reason` обрывает предсказанную
отдачу (D7). Ложные вспышки исчезают, а снимок 20 Гц и без того несёт 5 байт на
игрока.

## Risks / Trade-offs

- [Управление перестаёт «стрелять» раньше, чем игрок уследит] → клиентские
  врата остаются как есть (темп не меняется); меняется только то, что интент
  не теряется, а отказ виден.
- [Защёлкивание фронта добавляет состояние в кадровый цикл] → состояние
  локальное, одно поле, уже есть образец (`_dash_pending`) и покрывается
  детерминированным тестом без сети.
- [Отказ при пустом магазине теперь отправляется в снимок каждый кадр
  удержания] → решение кодируется дельтой (только смена значения), а не
  записью на каждый пакет.
- [Существующие тесты могут считать `shoot` вводом спускового крючка] →
  правки идти по `smoke_weapon_anim.py`, `smoke_combat.py`,
  `smoke_projectiles.py`, `smoke_hitscan.py`; новый детерминированный сценарий
  обязателен.
- [`smoke_projectiles.py` уже красный на чистом HEAD] → не использовать его как
  зелёный baseline; применить только к новым сценариям, общий падение не
  приписывать этому изменению.
- [Развёрнутый клиент 1.1.0 перестаёт подключаться] → так и задумано (D6):
  рукопожатие отказывает с «Обновите клиент», автообновление отдаёт сборку с
  версией 8. Проверяется `smoke_reliability.py` (несовместимый протокол).
- [Клиент, пропустивший снимок, не увидит подтверждения] → `fire_seq` монотонный,
  поэтому скачок счётчика читается как принятый выстрел даже без `state = 2` в
  этом снимке; анимация не зависит от одного потерянного кадра.

## Migration Plan

1. Клиент: защёлкивание фронта + отправка интента на каждом открытии врат
   (аддитивно, старый путь из ввода ещё работает — временное удвоение
   ожидаемо и проверяется тестом).
2. Сервер: решение по интентам + код причины; ввод перестаёт стрелять;
   `pl.state = 2` только по факту выстрела.
3. `PROTOCOL_VERSION` 7 → 8 вместе с полями `fire_seq`/`fire_ready` в записи
   игрока: это один атомарный шаг, иначе между шагом 3 и релизом клиента
   сервер и клиент разойдутся в разборе снимка.
4. Клиент: таймер локального оружия из серверного решения.
5. Откат: вернуть `PROTOCOL_VERSION = 7` и убрать два поля нужно **вместе** с
   откатом шага 4 — по отдельности стороны разойдутся в разборе `WORLD_STATE`.
   Шаги 1-2 откатываются независимо.
