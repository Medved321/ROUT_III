## Why

Клик на огонь теряется примерно через раз: игрок не видит ни выстрела, ни
урона. Причина не в балансе и не в потерянном пакете — у выстрела два дефекта,
которые дают этот симптом вместе.

**1. Фронт нажатия умирает в закрытых вратах темпа.** `shoot_pressed` живёт
ровно один кадр (`client/input_handler.py:104` обнуляет его в каждом
`update()`), а отправляется он только внутри условия врат и только при этом
фронте (`client/client.py:773-787`). Клик, попавший в закрытые врата, не
просто откладывается — он отбрасывается навсегда: к следующему открытию фронта
уже нет, и отправлять нечего. Для дэша тот же одно-кадровый фронт специально
защёлкивается в `_dash_pending` с комментарием «a single-frame edge is never
lost», а для огня этот приём не применён.

**2. Два пути выстрела на сервере и ноль сверки между ними.** Клиент держит
свой темп (`_next_fire_time`) и, не дожидаясь сервера, целиком проигрывает
отдачу (`client/client.py:782`, `_fire_anim_frames` → `gs.w_tmr`). Сервер при
этом стреляет из двух мест: надёжный `FIRE` с дедупликацией по `fire_seq`
(`server/server.py:264`) **и** флаг `shoot` в каждом пакете `PLAYER_INPUT`
(`server/server.py:319`, 25 Гц). `handle_shoot` при активном кулдауне молча
выходит (`server/weapons.py:151`) — без ответа, без события, без следа. А
`_apply_input` выставляет `pl.state = 2` по факту нажатой кнопки, а не по
факту выстрела (`server/server.py:326`), так что снимок мира тоже утверждает,
что выстрел был.

Итог: интент либо исчезает на клиенте до отправки, либо приходит на занятый
кулдаун и отбрасывается сервером — в обоих случаях без пули и без урона, а во
втором клиент уже показал отдачу.

## What Changes

- **BREAKING (поведение, не формат пакета):** флаг `shoot` в `PLAYER_INPUT`
  перестаёт быть спусковым крючком выстрела. Единственный путь выстрела —
  надёжный `FIRE` с монотонным `fire_seq`. Удержание кнопки порождает столько
  `FIRE`, сколько открытий ворот разрешает, поэтому удержание и одиночный клик
  идут по одному коду.
- Сервер перестаёт отбрасывать интент молча: решение «выстрел / отказ»
  доходит до клиента того же игрока (последний подтверждённый `fire_seq` +
  число тиков до следующего разрешённого выстрела) и попадает в снимок мира.
- Таймер оружия локального игрока перестаёт быть чисто клиентским предсказанием:
  отдача запускается предсказанием, но длительность и сам факт выстрела
  сверяются с сервером, поэтому подтверждённый выстрел обрывает анимацию, а
  отклонённый — не оставляет «зависшей» отдачи.
- `pl.state = 2` выставляется только когда выстрел действительно произошёл.
- Двойной выстрел из одного клика исключается на уровне сервера: `fire_seq`
  остаётся идемпотентным ключом, а вход из `PLAYER_INPUT` больше не добавляет
  второго выстрела.

## Capabilities

### New Capabilities
- Нет: проблема живёт в существующей боевой capability, новый контракт не
  вводится.

### Modified Capabilities
- `weapons-projectiles`: добавляется требование «каждый интент выстрела
  приземляется ровно один раз» и требование «отказ виден клиенту», включая
  сценарии удержания кнопки, клика быстрее кулдауна, потери/переупорядочивания
  надёжного канала и отсутствие двойного выстрела.

## Impact

- Протокол: `PLAYER_INPUT` (0x01) сохраняет поле `shoot` в бинарном виде без
  изменений; `FIRE` (0x27) без изменений. Подтверждение выстрела едет внутри
  `WORLD_STATE` в существующей записи игрока, куда добавляются три поля —
  `fire_seq` (uint32, последний принятый интент), `fire_ready` (uint8, число тиков
  до следующего разрешённого выстрела) и `fire_reason` (uint8, код причины
  последнего отказа: 0 — принято), то есть запись игрока растёт с 21 до 27 байт.
  `fire_reason` обязателен, а не украшение: без него клиент не отличит отказ
  («нет патрона») от ещё не дошедшего подтверждения, и удержание пустого
  магазина будет бесконечно «выстреливать».
- **BREAKING (формат пакета):** `PROTOCOL_VERSION` поднимается 7 → 8. Старый
  клиент читает длину имени из мусора сразу после записи игрока, поэтому молча
  разбирать новый `WORLD_STATE` не может; вместо этого версия отказывает ему на
  рукопожатии с уже существующим сообщением «Обновите клиент», а автообновление
  (`client/updater.py`) доставляет новую сборку. Плата — один цикл обновления
  для уже развёрнутых клиентов.
- Код: `client/client.py` (`_process_input`, `_fire_anim_frames`, `_update_local_state`),
  `client/input_handler.py` (`shoot`/`shoot_pressed`), `server/server.py`
  (`_on_player_fire`, `_apply_input`), `server/weapons.py` (`handle_shoot` — нужен
  возвращаемый результат вместо тихого `return`), `server/player.py`
  (состояние подтверждения), `shared/protocol.py` (разбор/сборка записи игрока).
- Тесты: `smoke_hitscan.py` (тайминги кулдауна), `smoke_reliability.py`
  (переупорядочивание `FIRE`), `smoke_projectiles.py` (шар виден обоим),
  `smoke_combat.py` (урон), `smoke_weapon_anim.py` (длительность отдачи).
  Нужен новый сценарий: клик быстрее кулдауна → N кликов = N выстрелов.
- Затрагивается надёжный канал: `FIRE` уже идёт по нему, но теперь является
  единственным носителем выстрела, поэтому регресс `smoke_reliability.py` на
  потерю/дубли/перестановку перестаёт быть опциональным.
