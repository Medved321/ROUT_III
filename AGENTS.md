# AGENTS.md

Проект: **ROUT III** — серверо-ориентированный FPS-шутер в стиле Doom 1
(DDA raycasting). Сотрудничество ведётся по спецификации openspec.

## Как мы работаем

1. Прежде чем менять код — прочитай активную спецификацию:
   `openspec/specs/`.
2. Все изменения фиксируются в `openspec/changes/` (ждём пользователя,
   чтобы заархивировать и обновить спецификацию).
3. Если спецификации нет или она расходится с запросом — сначала уточни,
   либо внеси правку в спецу через новый change.
4. Уделяй большое внимание оптимизации. Это важно!

## Стек и среда

- Python 3.12 (`py -3.12`), pygame 2.6, asyncio, UDP.
- Только stdlib + pygame. Сборка из исходников не требуется (3.12).
  Исключение: **numpy — обязательная зависимость только клиента** (перспективные
  флаты через surfarray, модуль `engine/np_flats.py`); сервер — всегда
  stdlib-only. Клиент без numpy при запуске автоустанавливает его (через pip);
  при неудаче остановится с явным сообщением. `tools/build_client.py` включает
  numpy в zipapp-артефакт.
- Оптимизация не трогает игровые механики: на любом качестве/железе работает
  полный набор механик (см. change `total-performance`), снижается только
  визуальная детализация.
- Формат пакетов: бинарный big-endian, описан в `SPEC.md`.
- Управляющие сообщения идут по надёжному каналу поверх одного UDP-сокета
  (`shared/reliability.py`: `RELIABLE_DATA`/`ACK`), игровой трафик — ненадёжный.
  Версия протокола — `PROTOCOL_VERSION` в `shared/version.py`.

## Граница движка

`engine/` — автономный рендер-пакет из 13 модулей: `constants`, `game_state`,
`framebuffer`, `quality`, `wallcache`, `np_flats`, `textures`, `sprite_cache`,
`particles`, `map_utils`, `sector_render`, `bsp`, `rendering`. Он импортирует
только stdlib, pygame, numpy (опционально) и контрактные модули
`shared.sector_map` / `shared.mt1`; `shared.map_data` запрещён. Он не знает о
`client.*`, `server.*` и сетевых модулях
`shared.protocol`/`reliability`/`version`; единственная связь с сервером —
формат карт `.mt1`.

Движок ничего не создаёт «с нуля»: спрайты и палитра тайлов приходят из
`engine.game_state` тремя слотами, которые заполняет `client/bridge.py`
(при импорте, то есть до первого кадра):

- `gs.sprite_provider(color, w, h, frame, state, pa, wpn, view) -> Surface` —
  поверхность бота; реализация — `client/sprite_factory.py`;
- `gs.enemy_surface_provider(kind, etype, px, frame=0, state='idle', view=0,
  detail=3, col=None, step=0, base=None) -> Surface | None` — модель врага,
  корпус и оверлеи состояния; реализация — `client/enemy_models.py`
  (`ENEMY_SURFACES`, диспетчер с закрытым `kind`: `model`, `corpse`,
  `shadow`, `stun`, `flash`, `rush`, `eyes`; рядом `clear()` и `stats()`);
- `gs.tile_provider(tile_char) -> str` — имя текстуры стены по символу тайла;
  реализация — `client/map_editor.py` (`TILE_CHAR_TO_TEX`).

Все три по умолчанию `None`, и рендер деградирует предсказуемо, а не падает:
боты рисуются пустой SRCALPHA-поверхностью, враги — светлым силуэтом-призраком
по размеру, стены — нейтральной текстурой `wall`. Откат моделей врагов без
правки рендерера — флаг `gs.enemy_models_enabled = False`. Любой внешний
потребитель (тест, мод) может подставить своего поставщика.

Кэшированные поверхности врагов вставляются в `gs.screen` напрямую
(`Surface.blit`), а не во фреймбуфер через `Frame.blit_mini`: внутренний буфер
масштабируется в окно вчетверо (`SCALE = 4`), и вставка через фреймбуфер
съедала бы разрешение в 4 раза. `Frame.blit_mini` и `engine.sprite_cache.mini`
остаются для ботов, предметов и частиц.

Враги — единственные сущности с 8 ракурсами: индекс ракурса
(`engine.sprite_cache.view_index`) — округление bearing до сектора 45°,
поэтому модель меняется только на границе сектора, а не каждый кадр. Состояние
анимации выводится в `client/bridge.py` из дельт снимка (движение, потеря HP,
lunge-дисplacement), потому что протокол передаёт только `id/x/y/angle/type/
hp/state` и менять его нельзя.

## Колоночная сетка глубин

`render()` возвращает и передаёт дальше буфер глубин по колонкам (`z_b`),
которым проверяется видимость спрайтов, ботов, игроков, частиц и тумана.
**Буфер — единственный источник истины о собственной сетке.** Перевод
экранного столбца `sx` в колонку делает ровно одна функция —
`engine/framebuffer.py: depth_col(z_b, sx, screen_w)`. Она берёт длину из
`len(z_b)` и возвращает `-1`, если колонки нет.

Пересчитывать колонку из настроек (`const.SCALE`, `gs.render_scale`,
`const.W`) нельзя: тайловый путь строит `const.W // SCALE` колонок, секторный —
`const.W // max(1, gs.render_scale)`, а это **разные настройки**, которые
адаптивный контроллер качества двигает независимо. Пока потребитель считал
колонку как `min(const.W // SCALE - 1, sx // SCALE)`, граница этого clamp'а
сама оказывалась за концом секторного буфера, и игра падала в игровом цикле с
`IndexError` в `engine/rendering.py` (change `depth-buffer-column-grid`).
`-1` — это «не видно», а не повод зажать индекс: зажим отвечает на вопрос о
соседней части экрана.

По той же причине `engine/sector_render.py` читает `W`, `H` и `FOV` из
`engine.constants` **в момент использования**: `from engine.constants import W`
фиксирует копию на импорте, а модуль импортируется лениво (на первом секторном
кадре), тогда как `const.W/const.H` переписываются на каждом ресайзе окна, а
`const.FOV` — в настройках. По значению импортируются только константы, которые
никто не переприсваивает (`TILE`, `TEX_W`, `CAM_Z`).

Модель тайлового редактора, палитра, списки сущностей и модели врагов живут
в клиенте: `client/map_editor.py` (рядом с `client/editor_screen.py` и
`client/sector_editor_screen.py`), создание спрайтов — в
`client/sprite_factory.py`, модели врагов — в `client/enemy_models.py`.
В `engine/` им не место; сканер
`tools/check_engine_imports.py` (AST всех `engine/*.py` + проверка состава
пакета: `sprites.py`/`map_editor.py`/`enemy_models.py` в движке запрещены +
запрет на ветку отрисовки по типу врага) прогоняй перед сдачей
ревью. Мёртвый дубликат `client/engine/` (старые копии модулей) не участвует в
границе и удаляется отдельной задачей.

## Запуск

```
run_server.bat                 # сервер на 0.0.0.0:7777
run_client.bat --name "Player" # клиент (меню → партия → игра)
```

## Игровые состояния клиента

`lobby ⇄ game`: меню (имя, список партий, P/R/Esc) → партия → игра.
Esc в игре открывает меню паузы (Продолжить / Настройки / Выйти в меню /
Выход). Из лобби доступны экраны Настроек (S) и Редактора карт (E).
Карту из редактора можно играть в мультиплеере: «▶ Играть» (F5) запоминает
карту, лобби показывает её и отправляет серверу в `CREATE_PARTY` (C — сброс,
лимит 64x64).

## Управление

Два равноценных режима переключаются в настройках (S) без перезапуска игры
(`config.json: control_mode`):

- **Мышь** (по умолчанию): WASD — движение, мышь — обзор, ЛКМ — огонь,
  `Пробел` — дэш, `↑`/`↓` дублируют `W`/`S`, Esc — пауза.
- **Трактор**: WASD — движение, `←`/`→` — обзор камеры (с разгоном, скорость и
  разгон настраиваются: `turn_speed`, `turn_accel`), `Пробел` — огонь,
  `Левый Shift` — дэш. Захват мыши выключен, курсор виден, `↑`/`↓` не дублируют
  `W`/`S` — они принадлежат камере.

Ровно одна кнопка на действие: в «Тракторе» `Пробел` не даёт дэш, а
`Левый Shift` не стреляет. Протокол для этого не менялся — те же `PLAYER_INPUT`
и `INPUT_FLAG_DASH`. Пробел в режиме «Мышь» не стреляет: огонь только ЛКМ
(плюс подтверждённый сервером таймер оружия в рендере — рендер не читает
раскладку клавиш как игровое состояние). Подсказки в лобби и в лог старта
партии берутся из `client.settings.control_hints()`.

В лобби: P — создать, R — обновить, M — режим, E — редактор, S — настройки,
C — сбросить кастомную карту. В редакторе: F5 — играть на карте.

## Размер окна

Окно клиента произвольного размера, включая 4K, и его можно тянуть мышью
(`RESIZABLE`). Размер живёт в `config.json: window_size` строкой `Ш×В`; в
настройках его можно листать пресетами от 640×480 до 3840×2160 (стрелки у
строки) или ввести произвольные габариты в поле `Ш×В` (Enter — применить,
Esc — отменить). Недопустимый ввод отвергается с сообщением, а не подменяется
молча. Границы — `client.settings.MIN_WINDOW` / `MAX_WINDOW`.

Внутренний буфер движка от окна не зависит: 4K не ухудшает внутреннее
разрешение и не меняет число лучей на кадр — платит только финальный
`transform.scale` и экранные элементы. `const.W`/`const.H` следуют за окном,
поэтому HUD, прицел и оверлеи позиционируются в экранных координатах, а
`RenderBridge.set_output_surface()` пересоздаёт `gs.screen` под новую сетку.

Меню (лобби, настройки, пауза, редакторы, подтверждение обновления) вёрстаны
на фиксированный виртуальный холст 1000×700 — `Renderer.ui`. `Renderer.present()`
масштабирует его в окно с центрированием чёрным; вызывающий код сам делает
`pygame.display.flip()`. Поэтому вёрстка меню не зависит от габаритов окна, а
под меню паузы виден замороженный игровой кадр при любом размере.

Отсюда правило, которое легко нарушить: **меню рисуется на холсте 1000×700,
события указателя переводятся в его координаты, хитбокс = нарисованный
прямоугольник, текст усекается**. pygame отдаёт `event.pos` в пикселях окна, а
геометрия меню — в координатах холста, поэтому каждый экран получает события
через `GameClient._menu_events()`, а обратное отображение живёт в
`Renderer.to_canvas_pos()` (вне холста, то есть в чёрных полях, — `None`, и
такой клик не активирует ничего). `Renderer.canvas_rect()` — единственный
источник геометрии вывода: и `present()`, и обратное отображение берут масштаб
и смещение оттуда. `InputHandler` в это правило не входит: обзор мышью идёт по
окну, а не по холсту.

Следствия, которые проверяет `smoke_menu_layout.py`:

- Прямоугольники элементов не пересекаются и лежат целиком в холсте; подписи
  берутся из ширины самой метки (`client/ui_layout.py`: `fit_width()`,
  `layout_row()`, `ellipsize()`, `clip_tail()`), а не из захардкоженных чисел —
  панель кнопок переносится, а не вылезает за край.
- Всё, что рисуется, и есть всё, что кликается: у экрана один источник
  геометрии на элемент (`_row_rect()`/`_value_rect()` в настройках,
  `_map_dropdown_geometry()` в списке карт), и hit-тест не расходится с
  отрисовкой. Длинное значение (4K-размер, длинный путь) усекается до своей
  полосы и не наезжает на стрелки.
- Клик по визуальному центру нарисованного элемента попадает именно в него при
  640×480, 1000×700, 1600×900 и 3840×2160.

## Обратная связь дэша

Дэш читается по авторитетному `state = 3` из снимка мира; протокол для этого
не менялся. Эффекты строит `RenderBridge._dash_fx()`: вспышка на фронте
`0 -> 3` и порция пыли на каждые `DASH_FX_TRAIL_PX` пройденного пути (не по
кадрам — иначе эффект зависел бы от FPS и сыпал пыль на месте при дэше в
стену). Свой дэш дополнительно взводит `gs.dash_fx`, и
`rendering.draw_dash_streaks()` рисует поверх мира горизонтальные полосы
скорости — между туманом и HUD, поэтому прицел и оружие остаются читаемыми.
Полосы гаснут по кадрам и в покое не стоят ничего.

## Обновление клиента

Собрать новую версию и сделать её актуальной:

```
py -3.12 tools/build_client.py --version 1.1.0 --set-latest
```

При подключении сервер сообщает версию (`HELLO_ACK`); если она отличается от
`CLIENT_VERSION` (`shared/version.py`), клиент показывает запрос и после согласия
скачивает артефакт, проверяет `sha256`, сохраняет отдельным файлом и
перезапускается. Откат — `client.updater.rollback`. Тесты: `smoke_reliability.py`
(потери/дубли/перестановки, раздача обновления, откат, несовместимый протокол).
